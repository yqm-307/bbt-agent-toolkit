# SOUL 校准：用真实历史把角色调到贴合用户

SOUL 写的是这个角色**怎么想、遇到选择时怎么选**。依据来自用户的真实历史：会话里的 bad case、长期记忆、用户纠正过的原话，而不是凭印象加规则。规则越堆越多时，agent 会把用户的偏好放大成繁琐流程，这正是校准要消除的东西。

## 何时用，何时不用

- 用：角色定位不对；agent 的流程、验证、审查、授权比风险重；回复让用户抓不住重点；SOUL 里堆满执行序、固定模板、纪律条文。
- 不用：只决定规则放哪一层、跨宿主兼容 → `harness-neutral-agent-prompts`；写项目规范（构建命令、目录、提交规则）→ 项目 `AGENTS.md`；只想压常驻 token → `context-prefix-slimming`；只写一张评审决策矩阵 → `decision-matrix`。

## 核心判断

1. **分层看内容跟着谁走**：跟着角色走的（意图、思维、行为、岗位职责、安全边界）放 SOUL；跟着项目走的（命令、目录、踩坑、门禁步骤）放项目 `AGENTS.md`。完整分层规范见 `docs/knowledge/agents-md-prompt-design.md` §5。
   - 反例：以「SOUL 放人格、AGENTS 放岗位」为界。岗位职责跟着角色走，应放 SOUL。
2. **SOUL 只写意图、思维、行为模式**。检验一条规则：换个项目还成立吗？它改变的是「怎么判断」，还是「按什么顺序做」？属于后者的移出 SOUL。
   - 反例：执行序 1–7、四要素回复模板、报告骨架。
   - 正例：把回复模板改写成意图：「每条回复按『隔几小时回来、只读这一条也能接上』来写」。
3. **每条都要能改变一个具体选择**，做不到的口号删掉。抽象规则配正反例，反例优先取真实 bad case，比如「只让诊断为什么慢，却做成了插件和评测流水线」。
4. **风险决策降权**：表开头写明「平时不用这张表」，只列真正有风险的情形（不可逆或外部写入、受保护文件、记忆与规则写入、大投入、超范围或改方向）。每行写「情形 | 用户的取舍 | 做法」，「取舍」一列来自用户视图，不是通用最佳实践。
5. **安全边界原样保留**，其他条文不得放宽它。实质约束不能当冗余删，例如：直连存储默认只读、超出授权边界就暂停并重新取得授权、动手前确认目标、范围和调用关系。
6. **依据先于措辞**：对用户的每句描述都要能在用户视图里找到依据；没有依据的，不写成「你一向……」。

## 流程

### 0. 定范围

先确认四件事：
- 目标角色的正式文件与加载入口：是否软链、加载字符上限、新会话还是当前会话生效。
- 是否命中保护路径，审查档位是什么。
- 是否允许提交（默认不提交）。
- 用户这次提了哪几条要求，逐条记下，作为最后对照的清单。

### 1. 挖 bad case（最贵的一步，按需裁剪）

- 用户已经明确指出问题时，直接用用户原话作依据，跳过这一步。
- 先建会话索引：id、来源、父会话、消息数、工具调用数、token、子代理数、主要工具。按指标挑候选会话，不盲扫。
- 按方向一次性并行派只读子代理。方向示例：检索与认知路径、验证与测试过度、流程与审批过度、委派开销、范围蔓延、工具与重试摩擦。判定标准、输出格式和红线写进同一份公共说明，模板见 [references/templates.md](references/templates.md)。
- 报告回来后：
  - 自己读原文，并抽查原始数据：计数的量级、用户原话是否真在所述消息里。子代理的自述不算结论。
  - 按根因汇总：主题、条数、最典型一例、诱因、现稿是否已覆盖。
  - 这一步只收集，不改任何东西。

### 2. 整理用户视图

- 分五类：在意、反感、纠正过（写出背后的偏好）、定过的（涉及风险且仍有效）、长期在推进。
- 每条附依据：日期、会话 id 或原话。
- 写明局限，例如记忆汇总接口失败、不是全量；标出已被推翻的旧记忆。
- 放在临时目录，不进源码树。它是 SOUL 中「我所了解的用户」和「风险决策」两节的素材，SOUL 里只放提炼后的稳定部分。

### 3. 改写候选稿

- 先备份当前稿。在临时目录写候选稿，不直接改正式文件。
- 参考骨架：
  1. 身份与使命
  2. 性格与取向（带反例）
  3. 我所了解的用户
  4. 理解意图
  5. 与用户相处
  6. 协作与委派
  7. 风险决策（平时不用）
  8. 边界与安全（原样保留）
  9. 宿主适配（具体工具名只出现在这一节）
- 被移出 SOUL 的步骤、模板原文存成一份「移出清单」，供项目 `AGENTS.md` 取用，不直接丢弃。
- 自检：
  - 安全节和宿主节与正式版 diff 逐字一致。
  - 无行尾空白；称呼用户不用性别代词。
  - 工具名只在宿主节出现。
  - 长度在加载上限内。

### 4. 独立审查

- 命中保护路径，或实质改变了角色定位时，交给没参与编写的人做一轮只读审查。
- 审查包要写清：用户原始要求、硬约束（违反即阻塞）、重点检查项、停止条件、JSON 格式的 verdict。模板见 [references/templates.md](references/templates.md)。
- 读报告原文，逐条核对：
  - 报告里的事实断言也要核实。例：报告称角色文件有字节上限，实际那条门禁只管仓库根文件。
  - 报告给的替换文本自相矛盾时不照搬，改为自写，并标明自写部分未经复核。
- 收敛规则：一轮审查，至多再一轮复审；剩下的只是照审查原文替换的措辞时，就算已覆盖，不再开复审。

### 5. 落盘

依次执行：
1. 去掉行尾空白。
2. 用时间戳备份正式文件。
3. 用候选稿覆盖正式文件。
4. 用 `cmp` 确认候选稿、正式文件、加载入口三方一致。
5. 跑仓库门禁。
6. 追加变更记录：背景、改动、依据、审查、门禁、回滚点。

不提交，等用户授权。告诉用户新会话才生效。

## 坑

- 用户纠正方向时，立即停掉原路线：旧稿另存，按新定位重写，不在旧稿上修补。
- 记忆汇总类接口可能整批失败：不原样重试，降级为检索结果加 bad case，并在用户视图写明局限。
- 门禁里与本次无关的 WARN，如实说明，不顺手处理。
- 发散建议只提不做，例如把用户视图做成定期刷新的心智模型、修正过时的长期记忆。写记忆、建规则等用户授权。

## 完成标准

- 用户提的每条要求，在新稿中都能指出落点。
- 内容丢失核对：被删的实质内容，要么在新稿里，要么在移出清单里。
- 安全节逐字一致；审查无阻塞项；门禁 FAIL 为 0；回滚点存在；未提交。
