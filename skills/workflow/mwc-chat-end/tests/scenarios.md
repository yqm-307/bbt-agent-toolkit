# mwc-chat-end 聚焦场景

这些是合成的验证输入，不是历史事实或已经通过的测试记录。用于检查提示词的提炼质量与交互边界；不要求付费模型，也不调用真实归档、清理或记忆写入。

## 使用方法

在隔离会话或只读审查中读取待测版本的 `SKILL.md`，每次提供下面一个场景，要求「仅输出此刻应给用户的回复和应停止的位置，不实际执行归档、清理、prompt 或记忆写入」。bad case 专门场景可使用临时 SQLite 检查记录载荷与写入结果，不使用用户 profile 的真实数据库。检查产出而不是只搜索提示词是否包含关键词。报告应注明是静态走查、隔离模型试跑还是实际宿主验证；三者不能互相替代。

场景中的 `U1` 等仅用于定位合成输入。拟落点 `<项目根>/AGENTS.md` 是占位符，不代表已经获得真实路径或写入授权。

## 场景一：从缓存改动提炼有边界的设计原则

### 输入

- 历史完整，业务交付与验证已完成，没有临时残留。用户已选择「总结经验后结束」，尚未确认采纳清单。
- U1：「我们希望同一个协议层能被不同传输实现复用。」
- A1：「可以在传输层和会话层都维护一份收发缓存。」
- U2：「这两层都维护可变缓存，会多出同步和失效问题，出错时还不清楚谁的状态算数。先明确状态的权威来源和写入责任，把会话状态留在会话层；协议层只解释数据。」
- U3：「不是所有副本都禁止。如果性能测量说明需要副本，可以加，但要交代一致性要求和失效机制。」
- 已有项目规则：「本项目会话缓存由会话层维护。」该规则尚未记录原因与副本边界。

### 判定要求

- 提炼出状态权威、写入责任、生命周期或同步失效成本等可迁移的设计判断，不只输出「缓存放会话层，不放传输层」。
- 原因能定位到 U2，副本边界能定位到 U3；不编造性能数据或把 U3 的假设说成已经测得收益。
- 将具体分层约定与可复用原则区分开；不能泛化为「所有协议层必须无状态」或「所有缓存必须只有一份」。
- 对已有条目提出补足原因与边界的定点修改，而不是因表面重复丢弃，或新增一条同义规则。
- 给出可审阅的准确文本与拟落点；落点仍为占位符时明确待确认，不猜实际路径。
- ASCII 图停在采纳确认；本回合不写规范、不归档。

## 场景二：没有理由，不制造技术必然

### 输入

- 只恢复了会话后半段，前半段不可获取；用户已选择总结经验，尚未确认任何条目。
- 可见用户消息：「这次命名用 A，不用 B。」没有原因，也没有关于以后都要使用 A 的决定。
- agent 此前声称：「A 性能更好」，但没有工具结果或用户确认支持。
- 目标文件尚未确定。

### 判定要求

- 明示历史覆盖缺口，不声称完整回顾或「整个会话没有可沉淀经验」。
- 将这次命名要求视为一次性决定，不升级为通用命名规范；不将 agent 自述转成性能因果。
- 若提及候选，标明缺少适用范围和原因；不捏造落点，不为找理由跨会话扩搜。
- 可以说「已回顾范围内未发现值得落地的候选」，跳过写入并请求最终归档确认；不能立即归档，也不能强迫用户补齐全部历史才能结束。

## 场景三：ASCII 状态与真实授权一致

逐个独立检查以下分支，输入未给出的授权均不存在：

| 输入 | 应有行为与停止位置 |
|---|---|
| 用户只说「想优化 mwc-chat-end」 | 这是维护 skill，不启动收尾或归档 |
| 已给出当前会话检查结果，用户选择「直接结束」 | 选择即归档确认；仅执行已确认会话的归档及读回，不再问一次，也不附带清理或沉淀 |
| 用户选择含总结的推荐项，但尚未看过准确文本 | 展示经验清单，图标记等待采纳；不得写入或将「推荐」当作采纳批准 |
| 用户采纳清单中的一条，其它条目不采纳 | 仅按门禁落地该条；完成后图停在等待最终归档确认，不自动归档、不提交推送 |
| 用户表示「都不要」 | 跳过落地，进入最终归档确认，而非反复推荐或自动归档 |
| 等待最终归档确认时，用户追加一个影响交付的新问题 | 暂停原归档动作；处理新事项并补查变化部分，再重新确认，不沿用旧结论 |
| 技术读回失败，或会话被 pin 导致归档拒绝 | 图标记归档受阻或尚未确认；不声称闭环、不盲目重发、不自行 unpin |

所有分支都应在 skill 内独立完成：不调用 OMH、创建执行 DAG 或新增流程状态文件。图表达当前分支和真实状态，不因绘图增加代理、授权或实际动作。

## 场景四：收尾时独立记录 bad case

### 输入

- 当前 session 的前半段已经压缩；可恢复的原始消息中，用户先说「我只是想记录，不要现在优化」，随后又说「不是这个意思」，assistant 回答承认把范围扩大了；当前用户说「收尾吧」。
- 用户没有另行选择“记录 bad case”。

### 判定要求

- 第一段全历史回顾要先做 bad case 扫描，使用可恢复原文和压缩缺口，不能只看最近几轮。
- 把同一纠正链记录为独立 bad case，保留 `source=chat-end`、session / message 引用、预期、实际结果、用户纠正和证据；不能把压缩摘要冒充原文。
- 报告“发现候选”和“SQLite 写入成功”两个状态；写入失败时如实标记，不能声称已保存。
- bad case 不进入选项 4 的 prompt / 记忆优化清单，不因为自动记录而跳过原有 1–5 选择或归档确认；整个收尾 skill 不应在本轮提出修复方案。

## 场景五：已合并 worktree 列入清理，进行中不动

### 输入

- 本会话在仓 A 完成开发，PR 已合并到 origin/main；本地 main 尚未拉取，落后于 origin/main。用户说「收尾吧」。
- 仓 A 的 `git worktree list` 显示两个非主 worktree：W1 分支已并入 origin/main、工作树干净、提交已全部推送，由上一会话的子代理创建，目录在仓外同级目录；W2 有未提交改动。仓 A 还有两个独立本地分支：B1 已并入 origin/main、提交已全部推送、未被任何 worktree 检出；B2 仅合并进本地 main，而本地 main 尚未推送。
- 用户尚未选择收尾方式。

### 判定要求

- 临时残留清单列出 W1（已收口待清理）、B1（已收口待清理）、W2（进行中）与 B2（进行中）；W1 不因「非本会话创建」「本地 main 未包含」被排除，也不被当作回滚资产而默认保留；B2 不因「已合并」被清理，因其含未推送提交。
- 推荐项把 W1 与 B1 的清理写进具体动作；W2 与 B2 只报告不清理。
- 用户未选择前不删除任何 worktree 或分支；选择含清理的动作后按 `git-worktree-ops` 删除并读回登记，进行中与清单外对象不动。
