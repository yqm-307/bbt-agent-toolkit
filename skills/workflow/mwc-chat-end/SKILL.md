# mwc-chat-end — 结束聊天前的检查、选择与归档

用户想结束聊天时用：先替用户核对「能不能结束」，把检查点讲清楚，再给 1–5 选项让用户一次选定怎么结束。会话盘点、闭环判断和归档确认由当前主 agent 亲自完成，不得委托；必要的独立代码审查或专业执行可以委托，结果仍由主 agent 验证。

## 目标与触发

用户说「结束聊天」「收尾」「预归档」「检查一下，准备归档」「归档吧」或点名本 skill 时执行。仅讨论、阅读或修改本 skill 不算结束指令。不自动触发，不给简单会话强加流程。

**结束指会话归档（WebUI，或官方 WebApp / 桌面端），不是另写 summary 文件。** 归档可恢复，不删除聊天记录、工作区或服务。

## 交互状态：独立流程，ASCII 展示

本 skill 独立运行，不依赖 OMH、DAG 工具或子代理编排。下面是交互分支，不是需要另外创建的执行任务。主 agent 用当前对话和内部 todo 维护状态，不另建状态文件；内部待办不算业务未完成项。

```text
检查交付 + 回顾证据
        |
   扫描并记录 bad case
        |
   用户选择收尾方式
        |
        +-- 补缺口 / 先不结束 --> 处理或暂停（再收尾时重新检查变化部分）
        |
        +-- 直接结束（选择即确认）-------------------------------+
        |                                                       |
        +-- 清理残留 --------------------------+                |
        |                                      |                |
        +-- 清理 + 沉淀经验                     |                |
                  |                            |                |
             提炼原则与边界                    |                |
                  |                            |                |
             查重、拟定准确文本                |                |
                  |                            |                |
             用户确认采纳                      |                |
                  |                            |                |
             按门禁落地、验证 -----------------+                |
                                               |                |
                                          用户确认归档 ---------+
                                                                |
                                                          执行归档、读回
```

- **展示当前分支，不铺满全图**：首次检查汇报、经验清单确认、最终归档确认时，在结论后用一个短 ASCII 路径标明进度，例如：

  ```text
  [完成] 检查与选择 -> [完成] 原则提炼 -> [等待你] 采纳确认
                                            |
                                      [未开始] 落地 -> 确认归档
  ```

  使用 `[完成]`、`[当前]`、`[等待你]`、`[受阻]`、`[跳过]`、`[未开始]` 区分状态；只有真实完成才标完成，写清当前在等谁、等什么。不适用或用户未选的分支直接省略；短会话可压成一行。
- **图只说明状态，不授予权限**：选择、写入和归档沿用下文各自的确认要求；等待时停在对应节点，不能把展示出来的后续步骤当作已经获准执行。
- **分支明确结束**：无候选或用户全不采纳时，跳过落地，进入归档确认；清理为空时标跳过。用户选择暂不归档则保留会话，归档入口受阻则说明手动操作方式，不把受阻画成完成。
- **恢复不重来**：用户只回复选择时，从当前等待点继续；上下文缺失先恢复本会话记录。用户新增事项或改变决定时，只使受影响结论失效，按下文重新确认，不沿用过期授权。

## 第一段：检查并汇报检查点

1. **圈定范围**：从本会话工具痕迹、交付目标与授权盘点产出和临时资源。上下文不足时用 `session_search` 补本会话记录；Git 状态与差异只是线索，不能把所有脏文件都归本会话。不做全盘扫描；非 Git 目录按不适用处理。
2. **核验适用项**（不适用的写明不适用，不扩大目标）：
   - 交付目标及必要验证已完成，有真实证据。
   - 本次应提交、推送、合并的变更达到约定状态。
   - 本次要求的部署、生效验证和运维记录已完成。
   - 目标内未完成事项已完成，或经用户明确取消、转交到可追踪去处；仅写进 summary 不算处置。
   - 本会话临时资源的现状：临时文件（scratch、一次性脚本、导出）、后台进程/端口/隧道、测试服务/容器、linked worktree 与本地分支。**此处只盘点并列清单，不动手清理**，是否清理由第二段用户选择决定；未确认归属的不列入清理对象，已核实收口的 worktree 与分支除外（见下条）。
     - worktree 与分支盘点：在本会话碰过的每个仓执行 `git worktree list`（worktree 常在仓外同级目录，主仓 `git status` 看不到），按 `git-worktree-ops` §4 逐个判定非主 worktree：分支（detached HEAD 按其提交）已并入 main 或 origin/main（本地 main 落后时以 origin/main 为准）、工作树干净、无未推送提交（`git log HEAD --not --remotes` 为空）＝已收口待清理，列入清理清单；有未合并提交或未提交改动＝进行中，只列不动。独立本地分支须同时满足：提交已并入 main 或 origin/main、无未推送提交（`git log <branch> --not --remotes` 为空）、未被任何 worktree 检出、不是 main 本身，才列入清理清单；仅合并但含未推送提交的按进行中只列不清。收口与否按 Git 状态判定，不按创建会话归属排除——这是上面归属门禁的唯一例外，清理仍须经用户选择授权；子代理为本会话任务创建的 worktree 归属本会话。
3. **回顾全历史，先扫描 bad case，再反思可沉淀经验**：由主 agent 回看本会话从开始到当前的用户消息及相关助手回应，重点找用户的矫正、反驳、指导、方案取舍及其理由，也保留踩坑实测和已证实有效的做法；不只看最近几轮，不只按关键词找。
   - **核对历史覆盖**：完整历史已在上下文中就直接复用；有压缩或缺失时，用宿主提供的本会话历史读取 / 检索能力补齐，检索命中只作定位，还须读相关上下文；不跨会话扩搜，不以压缩摘要代替完整回顾。取不全时，在检查点标明已回顾范围与缺口，只列已核实候选，不能声称「已回顾全历史」或「没有可沉淀经验」；缺口不强制阻止用户结束会话。
   - **独立扫描并记录 bad case**：按 `mwc-bad-case` 的口径，从同一份可恢复历史中找出目标未达成、用户明确纠正 / 否定 / 表达不适、被迫重述或未经授权动作等坏体验。连续纠正链合并为一个事件，不同目标或证据链分开；证据弱但有定位依据的记录为低 `confidence`，不凭语气补写感受。
   - **记录先于沉淀**：对可证据定位的 bad case 默认直接写入独立 SQLite，`source=chat-end`，保留 session / message 引用与历史缺口；写入失败必须单独报告，不能把找到候选说成已保存。bad case 记录不需要用户选择 4，也不进入 prompt、skill 或长期记忆优化清单；扫描完成后停在观察记录层。
   - **收集提炼依据**：不只记用户说过的「用 A、不用 B」，还要找当时的目标、限制、失败机制、方案代价，以及为什么接受另一种做法。合并同一原因导致的多个现象，按下文「经验提炼方法」形成候选主题；用户选择总结后再细化准确文本，不重复回顾全历史。覆盖用户纠正，也覆盖有证据的架构取舍、代码设计、验证方法与有效实践；这些是查漏视角，不是必须凑齐的分类。
   - **查重并选落点**：读拟落点的现状；已有规则或记忆完整覆盖的不重复新增。若已有条目只记了做法，而本会话补足了有价值的原因、边界或例外，候选应是完善原条目，不另立同义规则。角色 / 协作行为归对应角色 prompt，项目约定归项目规范，专项方法归已有 skill，可跨会话复用的偏好、经验或历史原因可归长期记忆（如 Hindsight，明确目标记忆库）；优先在最贴近职责的一处维护，不把整段会话写入记忆，也不为了沉淀新建资产。同一经验需要规则与背景分存时，分清职责，不双写同一规范。
   - **只列经验候选，不写入**：这里的“不写入”只针对 prompt、skill 和长期记忆的经验候选；bad case 已按上一条独立记录。检查点汇报历史覆盖情况及值得沉淀的候选、依据和落点；用户选择总结后复用这份盘点，进入第二段的清单确认，不重复回顾全历史，也不把发现经验当作写入授权。
4. **复用证据，补缺不重跑**：已有审查、测试及验收内容未变且仍适用时复用，新变更只补查影响面；运行态等易变事实按风险只读刷新；未知或验证失败不算通过。
5. **确认归档入口**：运行下方脚本 `check`，确认当前会话平台（WebUI / 官方 WebApp·桌面端）、会话 ID、profile、归档状态，以及是否被 pin（WebApp 侧被 pin 会挡住归档）。它只证明技术入口，不代替业务检查。平台不支持（CLI、cron、subagent 等）或受限环境仍可完成检查，但不得声称能代执行归档。

### 汇报格式

结论先行，让用户一眼看出能不能结束；检查点用短表，不铺日志：

> **可以结束 / 暂不可结束：<具体缺口>。**
>
> | 检查点 | 状态 |
> |---|---|
> | 交付与验证 | 已完成 / 缺口：… |
> | 提交 / 推送 / 部署 | 已完成 / 不适用 / 缺口：… |
> | 未完成事项 | 无 / 已转交到 …  |
> | 临时残留 | 无 / 清单：… |
> | 历史回顾 / 可沉淀经验 | 已回顾全历史：无 / 候选：… → 落点 …；或仅回顾 …、缺口 … |
> | Bad case | 已扫描并记录：<数量、ID、标题>；或未发现 / 写入失败：…；历史覆盖：… |
> | 归档入口 | <WebUI / WebApp> 可用 / 受阻：… |
>
> 请选：
> 1. **推荐：<本次具体动作，如「清理残留 + 沉淀经验后结束」>**：agent 按上面盘点给出的综合方案，写明含哪些动作和对象。
> 2. **直接结束**：只归档，不做其它动作；这个选择本身就是归档确认，不再二次询问。
> 3. **清理残留后结束**：先清理上面列出的临时资源（含已核实收口的 worktree 与分支，不限创建会话），再请你确认归档。
> 4. **总结经验并更新 prompt / 长期记忆后结束**：先清理残留，再列出值得落地的经验、拟改文件或目标记忆库及内容，等你确认后落地，再请你确认归档。
> 5. **先不结束**：继续处理缺口，或取消结束。

- **1 恒为推荐项，位置不变**，由盘点决定：有残留就含清理；有值得沉淀的经验就含总结；都没有就是「直接结束」；有阻塞就是「先补缺口：<具体动作>」（不归档）。1 要写成具体动作，不能只写「推荐」，用户回「1」即可照做。2–5 固定不变，不因推荐而增删或改序。
- 用户也可以组合，如「3+4」，按并集执行；4 已含清理，所以 3+4 等于 4。2 和 5 不与其它选项组合。
- 清理清单为空时说明「无需清理」；仅选择含总结的动作才汇报经验清单，清单为空时按第二段的历史完整 / 不完整分支表述。不凭空造活，仍进入「最后一步：确认归档」。只有选 2（以及 1 展开成纯「直接结束」）不再二次确认。
- 有阻塞时 1 是先补缺口；用户仍选 2–4 的，带着缺口结束是用户的决定，归档可恢复，把遗留缺口原样写进结束回复，不隐藏风险。
- 单纯归档入口受限：说「收尾已完成；自动归档受阻：<原因>」，按平台请用户手动归档（WebUI 侧栏归档；WebApp / 桌面端侧栏 Archive）。被 pin 挡住时先问是否 unpin，不自行解 pin。

## 经验提炼方法：从事件到设计判断

目标是让未来面对**相似问题、不同实现**时仍能作出判断，而不是记住这一次选了哪个 API。先保留证据，再抽象；展示时原则在前，具体做法作为依据或例子。不要求所有经验都上升为通用原则，也不为显得深刻而扩写。

1. **还原事实与约束**：当时要达到什么目标，哪里不妥，有哪些不可忽略的限制？区分用户明确决定、工具实测、agent 推断。用户明确约定可以保留为约定；一次成功或一次纠正本身不能证明一个普适因果关系。
2. **找到原因与代价**：什么机制使原做法在这些条件下出问题，新做法解决了什么，又付出了什么代价？「更规范」「更灵活」「更易维护」只是评价，不是原因；应能说明具体减少了哪种耦合、状态协调、误判或其它成本。原因未被说明或核实，就标记「原因未知」或「推断待确认」，不补写成已证实事实。
3. **提炼决策原则**：去掉偶然的文件名、工具名和实现细节，问「因此，下一次设计或决策时，应先考虑什么、由什么条件决定做法？」保留能指导选择的判断维度，而不只是扩大「用 A、不用 B」的适用范围。可写成「由于 <机制与代价>，在 <条件> 下设计 <对象> 时，应先明确 / 权衡 <关键因素>，再决定 <做法>」。这是思考支架，不是必须套用的句式；具体 API 或命令若正是边界所在，不强行抹掉。
4. **检查迁移与反例**：换一个实现后，这条判断还有用吗？哪个条件变化会让建议翻转，或者需要额外机制？至少说明有意义的适用边界；不知道例外时诚实保留未知，不凑反例。假设场景只能帮助检验表达，不能冒充第二份实测证据。
5. **选对层级并收敛**：有依据、可迁移的留下为原则；绑定当前项目的留下为局部约定；操作步骤归可复用方法；纯偏好不要包装成技术必然。缺依据或仍有争议的只列待确认，不自动写成规范。前后冲突以用户后续明确纠正为准，无法消解则说明冲突。能由一条原因解释的重复条目合并，不按每次纠正生成一条规则。

**提交给用户前的质量检查**：原因可追溯、判断能指导下一次选择、边界没有超出证据。若只剩「A 优于 B，因为 A 更好」，回到原因；若只剩「关注可维护性、遵守单一职责」，回到具体需要判断的因素。因果依据不足时降级为局部约定或待确认项，而不是无限追问或扩大检索范围。

示意对照（假设场景，非已验证的项目结论）：

- **只记动作**：「不要在两层分别维护同一份缓存。」
- **空泛口号**：「设计时要遵循单一职责，降低耦合。」
- **可迁移的判断**：「多个层独立维护同一份可变状态，会引入同步、失效和故障定位成本。因此，设计分层时，应先明确状态的权威来源、写入责任与生命周期，再决定是否需要副本；确需副本时，要明确一致性要求和失效机制。」

最后一种保留了原因、需要考虑的因素与副本这一例外；具体缓存放在哪一层属于该项目的落实方式，不冒充通用结论。

## 第二段：按选择执行并归档

只在已经针对**当前会话**给出上面的汇报与选项，且用户随后明确选了 1–4 或其组合如 3+4（或「直接结束」「清理后结束」「总结后结束」「按推荐」等同义回复）时执行。选 1 就先展开成它写明的具体动作，再按下面对应项执行。讨论方案时的「可以」不能充当选择。上下文缺失则查本会话记录，不猜。

用户回来期间若有实质变更、目标增加或证据失效，原结论失效：只补查变化部分，重新汇报并重新给选项。只有选择回复、无新增事项，不重跑全套检查或审查。

按选择：

- **5 先不结束，或选 1 而它写明「先补缺口」**：只处理缺口，不归档。处理完后只补查变化部分，重新汇报并重新给出 1–5，不沿用旧的选择或确认。
- **2 直接结束**：选择即归档确认，直接归档。选 1 而它写明的就是「直接结束」时同此处理，不再问第二遍。
- **3 清理残留**：只清理第一段列出的临时资源，清理后读回确认；不误停正式服务、不删回滚资产，清单外的东西一律不动。已核实收口的分支与其 worktree 不是回滚资产（合并提交本身即回滚落点），按 `git-worktree-ops` 删除并读回。删除生产对象或其它缺授权动作，列明对象和影响后等用户决定。
- **4 总结经验并更新 prompt / 长期记忆**：先做 3，然后分两步，**写入前必须停下来让用户确认**，不得在同一回合里直接写：
  1. **列清单，本回合到此为止**：复用第一段全历史回顾的候选，按「经验提炼方法」细化，只列值得落地的经验，不改文件、不写长期记忆。门槛：来自本会话用户的矫正、反驳、指导、踩坑实测或被证实有效且会复现的做法；一次性的、现有 prompt / 记忆完整覆盖的不列（复用仍有效的查重结果，只补缺口）。每条写四项，不强行压成一句话：
     - **原则 / 约定**：标明层级，先讲可复用判断，再讲原因、适用边界与必要的例外。推断或原因未知时显式标记，不能为了凑原则伪造因果；具体实现只在有助理解时作为例子。
     - **依据**：本会话中可定位的用户原话或准确转述、工具证据及上下文，能追溯目标、问题和取舍原因；区分已观察事实、用户明确决定与 agent 推断，不冒充用户原意。
     - **落点**：文件路径或长期记忆的目标记忆库（如 Hindsight 的 bank），并标明是否受保护路径、长期记忆或新建 skill；目标不明确先确认，不猜。
     - **拟改内容**：新增 / 替换的原文或拟写入记忆的准确文本，能直接审，不写「补充说明」这类空话。
     末尾给默认建议（采纳哪几条），请用户回「全采纳 / 采纳 1,3 / 都不要」。清单为空时，历史完整才说「没有值得沉淀的」；历史不全则说「已回顾范围内未发现候选，仍有历史缺口」，随后进入「最后一步：确认归档」。
  2. **用户确认后落地**：只写被采纳的条目，做最小定点修改（不整体重写）；新建 skill 前先查重；写长期记忆、改受保护路径（如 `AGENTS.md`、门禁脚本等）时，清单里的拟改内容就是草稿；用户确认后，仍须先过仓库的预检与独立审查门禁，通过后才写入。选 4 和对清单的确认都不构成跳过门禁的授权，只有用户明确授权跳审才可跳过，并在提交说明里留痕。改了什么逐项报告，完成后进入「最后一步：确认归档」。「都不要」或未采纳的条目不阻塞归档，直接进入最后一步。

  用户对清单的确认只授权其中明确列出的工作区修改或目标记忆库写入，不授权提交、推送或部署。

选择只授权所选动作，**不附带提交、推送、部署或对其他会话的操作**；这些仍按原任务授权与对应门禁处理。按第一段清单清理已核实收口的 worktree 与分支不受创建会话限制。

### 最后一步：确认归档（选 2 除外）

选 3、4，或选 1 且它展开的动作含清理 / 总结，这些动作都做完后，**停下来、不自动归档**，用一条短回复汇报结果和遗留项，并以这个问题结尾：

> 请选：**1. 立即归档本会话（默认）** / 2. 先不归档

用户回「1」（或「归档」「好」等明确同义回复）就立即归档，不再追问；回 2 就保留会话，说明随时可再说「归档吧」。这一步要求用户在动作完成后明确回应，选择阶段的回复不能顶替。若这期间用户追加了新事项，先处理新事项，再重新问这一句。

归档用脚本对确认过的当前会话执行，并按平台读回：WebUI 走其 API，WebApp / 桌面端只读读回会话存储。读到 `archived` 为真且会话 ID / profile 一致后，才回复：

> **已结束并归档，本会话已闭环。**（附：本次执行了选项几，遗留项若有。）

归档过程中当前回复可以继续生成；不得为了看到该回复而自动恢复会话。已归档的重复请求只读确认，不再写入。

请求失败、超时或读回失败：说「归档尚未确认：<最短原因>」，保留待确认状态；先只读检查，不能盲目重发、直改数据库或假报闭环。用户手动归档的，能读回就验证，否则只说明尚未核实。

## 归档执行入口（按平台分流）

`scripts/session_archive.py` 只用 Python 标准库。平台由脚本按环境变量判定，不看会话标题或用户描述：

- **WebUI**（`HERMES_SESSION_PLATFORM=webui` + 12 位小写十六进制 `HERMES_UI_SESSION_ID`）：复用 WebUI 原生 API，不改 WebUI 核心、不直写存储。认证用宿主已提供的 `HERMES_WEBUI_PASSWORD`，仅内存登录 Cookie 并在结束时退出该临时登录；不读浏览器会话库、不伪造签名、不输出密码或 Cookie。**目标只能取 `HERMES_UI_SESSION_ID`**，`HERMES_SESSION_ID` 会随压缩变化，不可替代或作为回退。连接固定 loopback、禁止重定向与环境代理。前提缺失或 SSO-only 时停止脚本路径，改用手动归档。
- **官方 WebApp / 桌面端**（`HERMES_SESSION_PLATFORM` 为 `local` / `gui` / `desktop`，且 `HERMES_SESSION_ID` 或 `HERMES_SESSION_CHAT_ID` 匹配 `local-` 加 64 位小写十六进制）：归档就是该会话在 profile 会话存储里的 `archived` 标记。脚本先只读解析到当前行（行 id 优先；压缩后 agent id 会轮换成 `<时间戳>_<hex>`，此时按 `HERMES_SESSION_CHAT_ID` 回退，并跳过 `end_reason='compression'` 的旧段）和 pin 状态，再调用 `hermes sessions archive --chat-id <解析到的行 chat_id> --include-open --yes`，最后只读读回。`check` 输出的是解析后的行 id，`--confirm-session` 就用它，不用环境变量里的原始 id。
  - **pin 会挡住归档**：CLI 一律跳过被 pin 的会话（`--include-pinned` 只有 prune 有）。脚本直接拒绝并说明原因；是否 unpin 由用户决定，不自行解 pin。
  - `--include-open` 必须带：桌面端 / WebApp 会话从不写 `ended_at`，缺它会漏掉当前会话。
  - CLI 的选择键是 chat id（精确但 chat 级）：行 `chat_id` 不是 `local-*`（例如历史 adopted chat）或为空时可能命中同 chat 的兄弟会话，脚本直接拒绝，请用户改在应用内归档。
  - CLI 在独立进程直接写会话存储：不 bump 可见 revision、不会通知正在运行的网关（WebApp 侧栏约 20 秒轮询自行刷新，桌面端刷新时机未核实），但 `on_session_delete` 插件钩子仍会在该 CLI 进程内触发。
  - 行查询失败、CLI 未报告恰好 1 个会话、或读回不一致，一律按失败处理，不重发、不直改数据库。
- 其它平台（CLI、cron、subagent 等）：脚本明确拒绝，说明需手动归档。

`SKILL_DIR` 必须取本次 `skill_view` 返回的真实目录，不假定当前工作区就是技能仓库：

```bash
python3 "$SKILL_DIR/scripts/session_archive.py" check
# 仅在用户选定 1/2/3 后；<confirmed-session-id> 用确认过的字面会话 ID，不用标题匹配。
python3 "$SKILL_DIR/scripts/session_archive.py" archive --confirm-session '<confirmed-session-id>'
```

脚本的 `verified` 只表示归档状态经读回核验；是否闭环仍由主 agent 的业务检查决定。接口版本、ID 格式或 CLI 输出变化时先核实再适配，不放宽校验凑成功。

```bash
python3 "$SKILL_DIR/scripts/session_archive.py" self-test
```

脚本自检不发网络请求、不调用真实 CLI：覆盖平台识别与拒绝、压缩轮换后按 chat id 回退、WebUI 身份边界与压缩后 ID 保持、只读检查、精确写入、幂等、读回失败，以及 WebApp 侧的 pin 拒绝、确认 id 校验、adopted / 无 chat id 拒绝、CLI 计数校验与读回。真实接口 / CLI 变更另用一次性会话验证归档与恢复，不拿用户正在工作的会话做实验。

## 迁移适配说明

- 宿主：Hermes WebUI（命名 profile 模式）与官方 WebApp / 桌面端（网关承载）。环境变量 `HERMES_SESSION_PLATFORM`、`HERMES_SESSION_ID`、`HERMES_UI_SESSION_ID`、`HERMES_HOME`、`HERMES_WEBUI_PORT` 由宿主提供，WebUI 密码登录另需宿主已提供的 `HERMES_WEBUI_PASSWORD`；脚本不读浏览器会话库、不读密码文件。
- 运行时依赖：仅 Python 标准库，无第三方包；WebApp 侧另需 `hermes` CLI 在 PATH 上，找不到即拒绝。WebUI 连接只走 loopback、禁止重定向与环境代理。
- 平台边界：以上实测都在 Linux/WSL（Python 3.14.9）。Windows 原生宿主未适配也未验证——`state.db` 的 `file:` URI 按 POSIX 路径拼接，`hermes` 若解析为 `.cmd` 无法被 `subprocess` 直接执行，示例命令用的是 `python3`。
- 首次运行验证：`python3 <SKILL_DIR>/scripts/session_archive.py self-test`，输出 `PASS`（Python 3.14.9）。WebApp 侧另实测：`check` 读出 `platform=webapp`、`archived=false`；`hermes sessions archive --chat-id … --include-open --yes` 对已结束会话和从未结束的会话都归档成功并读回 `archived=1`；对正在运行的会话做过归档 → 读回 → 恢复往返。压缩轮换后（agent id 为 `<时间戳>_<hex>`、chat id 仍为原 `local-*`）的回退路径只由自检覆盖，未在真实压缩过的 WebApp 会话上验证。WebUI 分支只用注入的假 API 自检，真实 WebUI 归档、其它 Hermes 版本与 SSO-only 环境**未验证**；缺 `HERMES_UI_SESSION_ID`、平台不支持或 SSO-only 时按正文停止脚本路径，改由用户手动归档。
