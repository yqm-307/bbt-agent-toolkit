# 收尾检查与状态示例

## 交互分支示意

```text
检查交付 + 回顾证据
        |
   扫描并记录 bad case
        |
   用户选择收尾方式
        |
        +-- 补缺口 / 先不结束 --> 处理或暂停（再收尾时重新检查变化部分）
        |
        +-- 直接结束（选择即确认）-------------------------------+
        |                                                       |
        +-- 清理残留 --------------------------+                |
                                               |                |
                                          用户确认归档 ---------+
                                                                |
                                                          执行归档、读回
```

- **展示当前分支，不铺满全图**：首次检查汇报、最终归档确认时，在结论后用一个短 ASCII 路径标明进度，例如：

  ```text
  [完成] 检查与选择 -> [完成] 清理残留 -> [等待你] 归档确认
  ```

  使用 `[完成]`、`[当前]`、`[等待你]`、`[受阻]`、`[跳过]`、`[未开始]` 区分状态；只有真实完成才标完成，写清当前在等谁、等什么。不适用或用户未选的分支直接省略；短会话可压成一行。

## Worktree 和分支盘点

在本会话碰过的每个仓执行 `git worktree list`。主仓 `git status` 看不到其他工作树。按 `git-worktree-ops` 的盘点方法判断：

- **非主 worktree**：分支或 detached HEAD 提交已并入 main 或 origin/main（本地 main 落后时以 origin/main 为准）、工作树干净、`git log HEAD --not --remotes` 为空，才列为已收口待清理。有未合并提交、未提交改动或未推送提交的，只报告。
- **独立本地分支**：已并入 main 或 origin/main、`git log <branch> --not --remotes` 为空、未被任何 worktree 检出且不是 main，才列为已收口待清理。有未推送提交的，即使已合并也只报告。
- 只有已核实收口的 worktree 和分支可以跨创建会话列入清单。子代理为本会话任务创建的 worktree 归本会话。第一段只盘点，清理仍须按正文取得用户授权。

## 回顾本会话历史

3. **回顾全历史，扫描并记录 bad case**：由主 agent 回看本会话从开始到当前的用户消息及相关助手回应，重点找用户的矫正、反驳、指导、方案取舍及其理由；不只看最近几轮，不只按关键词找。
   - **核对历史覆盖**：完整历史已在上下文中就直接复用；有压缩或缺失时，用宿主提供的本会话历史读取 / 检索能力补齐，检索命中只作定位，还须读相关上下文；不跨会话扩搜，不以压缩摘要代替完整回顾。取不全时，在检查点标明已回顾范围与缺口，只记录已核实的事件，不能声称「已回顾全历史」；缺口不强制阻止用户结束会话。
   - **独立扫描并记录 bad case**：按 `mwc-bad-case` 的口径，从同一份可恢复历史中找出目标未达成、用户明确纠正 / 否定 / 表达不适、被迫重述或未经授权动作等坏体验。连续纠正链合并为一个事件，不同目标或证据链分开；证据弱但有定位依据的记录为低 `confidence`，不凭语气补写感受。
   - **记录是自动行为**：对可证据定位的 bad case 默认直接写入独立 SQLite，`source=chat-end`，保留 session / message 引用与历史缺口；不判断「值不值得记录」，不征求用户选择，写入失败必须单独报告，不能把找到候选说成已保存。
   - **记录即止**：扫描完成后停在观察记录层。本流程不提炼经验、不更新 prompt / skill / 长期记忆、不提出修复建议。bad case 的归并、定因与修复不属于本流程；`mwc-correct` 会读取库里的积累，`mwc-reflect` 由用户显式点名时单独运行。

## 检查点汇报示例

结论先行，让用户一眼看出能不能结束；检查点用短表，不铺日志：

> **可以结束 / 暂不可结束：<具体缺口>。**
>
> | 检查点 | 状态 |
> |---|---|
> | 交付与验证 | 已完成 / 缺口：… |
> | 提交 / 推送 / 部署 | 已完成 / 不适用 / 缺口：… |
> | 未完成事项 | 无 / 已转交到 …  |
> | 临时残留 | 无 / 清单：… |
> | Bad case | 已扫描并记录：<数量、ID、标题>；或未发现 / 写入失败：…；历史覆盖：… |
> | 归档入口 | <WebUI / WebApp> 可用 / 受阻：… |
