# mwc-correct 场景用例

这些用例用于检查规则是否覆盖关键分支，不代表已经运行模型评测。

## 1. 能用架构消除

输入：

> agent 总是直接调数据库客户端，不走 repository 层。

判定：

- 先试把客户端藏到 repository 模块内部，让外部 import 失败；做不到再退到 lint，并说明为什么架构层不行。
- lint 报错信息点名应该用的 repository 函数。

## 2. 只出现一次

输入：历史里只找到一次某个配置项没注册到 schema。

判定：

- 列出但不修，写明只出现一次。

## 3. 证明检查有效

输入：已经写好一条新检查。

判定：

- 在当初出错的那次提交上跑，输出失败；在当前修好的代码上跑，输出通过。两段输出都贴出来。
- 只用为证明而特意写错的样本，不算完成。

## 4. 规则已在表里却重犯

输入：对照表里有「新配置必须注册到 schema｜仅文档」，agent 又漏了。

判定：

- 视为重犯，在同一次改动里升级到类型或 lint 层，更新对照表的「由什么强制」一栏。

## 5. 改动范围

判定：

- 改动留在工作区或分支，不提交、不推送；改 agent 指令文件按目标仓库门禁走。

## 6. 用户点名处理 bad case 时的状态流转

输入：bad case 库里有 5 条 open 记录，其中 3 条是不同会话里「agent 绕过 repository 层直连数据库」，1 条是「某次沟通误解」，1 条证据只剩压缩摘要无法定位原话。

判定：

- 3 条同类记录互相构成「独立出现」，归并为一类；拟标 `reviewing` 的 ID 随归并结果一起给用户确认后再标记，不是每记一条就修一次。
- 「沟通误解」不属可强制错误，不套 lint；说明去向（`ignored` 或转 `mwc-reflect`），不让记录悬空。
- 证据不足的记录列出并说明，不静默跳过、不为了凑数降低归并标准。
- 改 `reviewing` / `resolved` / `ignored` 前列出拟改 ID 和去向等用户确认；用户不同意不写库。
- 修复验证通过后，`analysis` 里写清修复落点，不是只标状态了事。
