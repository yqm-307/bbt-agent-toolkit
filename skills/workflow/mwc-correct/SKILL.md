# mwc-correct — 让重复错误在仓库里犯不出来

用户总在为同一类错误纠正 agent 时，修仓库而不是修下一句提示词。假设每个贡献者都是只看过自己打开的文件、照抄最近的例子、走能编译通过的最短路径的 agent；让一个从单个文件看起来正确的改动，对整个仓库也正确。

改编自 pstack `/correct`（MIT，Copyright (c) 2026 Lauren Tan，许可全文见 [pstack-LICENSE.txt](pstack-LICENSE.txt)，[来源](https://github.com/cursor/plugins/tree/ca782ed8b3c2c521cead8e1720d55c3a5dbf2347/pstack)）。

## 1. 找错误类

范围是用户点名的仓库。用户点名了具体错误就从它开始；没点名就从历史里找。读：

- 近期提交、revert、review 评论，以及解释绕过办法的代码注释。
- 仓库的 agent 指令文件（如 `AGENTS.md`）和其中的规则对照表。
- `mwc-bad-case` 的记录（`list --status all`），有库时读，没有就写「未查」。
- `mwc-reflect` 转来的「转检查」条目。

把同一原因的错误合并成一类。**一类至少有两次独立出现才处理**；只出现一次的列出来，不修。

## 2. 选最高能生效的一层

| 顺序 | 层级 | 做法 |
|---|---|---|
| 1 | 架构 | 让错误路径不存在：每份状态一个所有者，每件事一种支持的做法；藏起内部实现让错误的 import 直接失败；手工同步的多份清单换成一个真源；删掉 agent 会照抄的旧做法和死代码。 |
| 2 | 类型 | 让错误状态写不出来。 |
| 3 | lint / CI | 错误代码仍能编译时加检查，报错信息直接说该用哪个文件、类型或函数。这种写法在仓库里已经很多时，只拦新增的。 |
| 4 | 测试 | 测行为。顺手修掉行为坏了还能通过、或只改内部实现就失败的测试。 |
| 5 | 文档 / agent 规则 | 只留给需要判断的事。agent 跳过它不会有任何报错，所以放最后。 |

人工 review 不在表里：每个 PR 都要靠人拦同一个错误，正是这里要消除的问题。

## 3. 修并证明

- 先修最常见的几类，每类一个独立改动单元。
- **用真实的历史错误证明新检查会报错**：拿当初那次提交的代码或 bad case 的现场跑一遍，看到它失败；再在修好的当前代码上跑，看到通过。只用为证明而特意写错的样本不算。
- 本地和 CI 跑同一条命令；仓库没有 CI 就写明只有本地命令。
- 例外写在出错的那一行，带原因、到期日和批准人。

## 4. 维护规则对照表

在目标仓库的 agent 指令文件里维护一张表，每条规则对应强制它的东西：

| 规则 | 由什么强制 |
|---|---|
| 数据库访问走 repository 层 | lint 规则 `no-direct-db` |
| 需要判断的约定 | 仅文档 |

用户又纠正时，先修这次的错误再补规则。规则已经在表里却没有任何强制手段，就算重犯，在同一次改动里按最高能生效的一层修掉。错误已经不可能发生时删掉那一行。agent 指令文件通常是受保护文件，改它按目标仓库的门禁走。

## 输出

每类一段：证据（提交 SHA、review 链接或 bad case ID）、选了哪一层、为什么更高的层不行、证明命令及其失败和通过的输出。只出现一次的和证据不足的单列，说清缺什么。处理完的 bad case 可建议标为 resolved，用户同意再写库。

## 边界

- 改动停在工作区或分支上，不提交、不推送、不开 PR；这些按目标仓库的授权与门禁另行取得。
- 新检查改变的是门禁本身：按目标仓库要求做独立审查，不自审放行。

## 适配与验证

- 适用宿主：能读写本地仓库并执行 shell 命令的 agent 宿主；Hermes 可用 `/mwc-correct`，其他宿主按 skill 名调用。
- 前置条件：目标仓库是 git 仓库；读 review 评论需要 `gh` 等平台 CLI，没有就标「未查」，不把缺访问写成没有记录；读 bad case 需要 `mwc-bad-case` 的库，没有就标「未查」。
- 纯提示词，无脚本。聚焦场景见 [tests/scenarios.md](tests/scenarios.md)，它们是判定要求，不是已运行的模型评测。
- 未验证：尚未在任何宿主的真实会话中运行，也未在真实仓库历史上实跑「找错误类 → 修 → 用历史错误证明」的完整流程。
