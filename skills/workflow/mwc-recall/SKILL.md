# mwc-recall — 上下文恢复

重建近期工作上下文，回答「之前在做什么、做到哪了、接下来该做什么」。

保持精简、聚焦主题。只读范围需要的线索，然后停。

上下文存在两个记录里。你的聊天历史记录了你做了什么和决定。共享记录（用户报告、之前的修复、线上事故）记录了同一代码在别人名下的遭遇。第二个记录跨越 git、issue tracker、聊天频道、长文档、错误追踪。一个 bug 尾巴很长的功能，大部分故事在那里，不要只从你的会话记录重建。

## 会话文件位置

Hermes 会话存在 `$HERMES_HOME/sessions/`（JSON 请求转储）和 `$HERMES_HOME/state.db`（SQLite，包含 sessions 和 messages 表），`$HERMES_HOME` 指当前 profile 目录。用 `session_search` 工具搜索本会话之前的对话，或查 `state.db` 的 messages 表按主题过滤。

## 步骤

1. **分类，再路由。** 恢复某个特定聊天是不同任务，把习惯变成可复用 skill 属于另一类任务。Recall 是跨近期聊天加载工作上下文再行动。如果用户已给了完整状态胶囊（路径、分支、改动），直接用，跳过挖掘。

2. **锁定范围再搜索。** 定窗口（「最近」是真实范围，默认最近 7 天）、定主题（如果指定）、定工作区（默认当前，不跨项目）。把范围说给用户听。不悄悄把「全部」变成「最近 N 个」。

3. **扇出搜索聊天历史。** 用 `session_search` 搜主题相关对话，或派并行子代理（快速便宜模型）各拿语料一片。告诉每个子代理按真实修改时间排（`ls -t`），不按 UUID 名，先 grep 主题再只读匹配聊天的相关区域，跳过当前聊天和明显噪音（子代理、eval、测试聊天）。每个返回同一 schema，每个聊天一块：主题、用户目标、决定、未结线程、挣扎和纠正、产物（PR、ticket、分支），各引聊天 UUID。一两个聊天时跳过扇出直接搜。原始 transcript 留在子代理，主线程只拿发现。

4. **扫共享记录，只要主题涉及功能、文件、子系统、区域或 bug。** 这是默认不是判断，「我的 X 工作」不豁免。查 git log、git blame、gh pr list、gh issue list、相关 issue 讨论。问「当前状态是什么、试过什么没成功、用户还在报什么」。跳过这步的唯一情况是纯活动回忆且没指定目标（「这周我做了什么」），此时自己的历史和实时状态就是全部答案。

5. **核实实时状态。** 把挖掘和扫描找到的 PR、分支、ticket 用 `git` 和 `gh` 查当前真实状态。当答案取决于 agent 实际做了什么（跑了什么工具、读了什么文件、报了什么错）时，读完整 transcript 不只是本地修剪副本。

6. **写简报。** 按输出契约交付。按线索分组。不跑题。

## 输出契约

先概要，再线索状态，再问题，再下一步。细节在下面或被砍。

- **概要**：最多 5 条。这工作是什么、整体进展。
- **线索**：每条一个状态标签：`[已合并 #N]`、`[PR 待审 #N]`、`[分支在做]`、`[已验证未提交]`、`[已回滚]`、`[已规划未开始]`。没标签的线索不算完成，标上。
- **问题**：最多 5 个反复出现的。包括用户还在报的症状和发出去又回滚的修复，让下次尝试从上次失败的地方开始。
- **下一步**：一个最具体有用的动作。

相邻功能或 ticket 除非阻塞这个否则不进。概要和线索超一屏时砍细节不砍线索。写简报时引用聊天发现用 UUID，共享记录发现用来源（PR #、ticket ID、聊天链接、错误追踪 issue），公开输出前脱敏。

## 迁移适配说明

- 依赖 Hermes 会话存储：`$HERMES_HOME` 下的 `sessions/`（JSON 请求转储）与 `state.db`（SQLite，`sessions`、`messages` 表），以及宿主提供的 `session_search` 工具。`$HERMES_HOME` 指当前 profile 目录；查其他 profile 需显式给出其路径。存储缺失或表结构变化时跳过该项并说明，不据文件名推断内容。
- 第 4、5 步的共享记录扫描与实时状态核实需要仓库本地 git 历史，以及 `gh` 等平台 CLI 的访问权限；没有时该步标「未查」，不把缺访问写成「没有记录」。
- 纯提示词，无脚本；未针对特定宿主或模型实测简报质量。
