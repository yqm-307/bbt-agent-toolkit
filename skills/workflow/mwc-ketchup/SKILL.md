# mwc-ketchup — 会话追赶

用户离开后回来，用大白话说清楚：发生了什么、哪些事在等他做决定。用户想结束聊天、归档会话时用 `mwc-chat-end`，不是本 skill。通知和子代理结果不算用户的消息。假设用户记得他最后一条消息，不记得之后的任何内容。

用大白话的语气：短句、不堆术语、像一个人跟另一个人汇报。说对用户改变了什么，不说你怎么做的。说「测试通过了」而不是「CI 绿了」。除非用户需要，不写哈希、文件路径、命令、构建号、测试计数。每个 PR、分支或 agent 用用户能认出的名字，不用你发明的标签。一个事实需要上下文才能理解时，给上下文或者不提。

## 收集发生了什么

本轮只读。只用已有材料做图：不改代码、不启动应用或任务、不发消息。收集你从那之后做的工作、子代理的报告、本聊天里其他人的消息。检查本聊天涉及的每个 PR、CI 运行或 agent 的当前状态。核对你要展示的每个数字和事实，改错要说出来。

一个行动项是只有用户能做的决定或步骤：产品选择、审批、不可逆操作、你没有的权限。包括之前提出但仍在等用户的。你还能自己做的工作不是行动项。**不凭空造行动项**。用户没要求且工作不需要的步骤不列，除非它是不可逆的且在等用户——给它一行，不给图。

一个行动可以覆盖多个项（比如一组 PR 等合并）。每个项收集：链接、对用户的影响、你推荐的证据、风险、你的推荐。不知道的事实写「未知」。没有的链接不写。

## 写回复

字数花在行动上，不花在过程上。发生了什么部分控制在 100 字以内（不算图），事少更短。去掉对用户没影响的工作。每个行动项约 30 字。回复随行动项数量增长：两个项远低于 150 字，三十个项会多很多。**不凑字数**：不为了控制在字数内砍行动项，不拿数字代替列表，不拿链接代替项。链接可以加深，但回复本身必须够做决定。

开头一句短句，说清什么在等用户，或者说没有。

然后展示发生了什么，图在前。内嵌工作产出的截图和视频，然后放解释改动的图。再一行总结用户要求的事：结果如何，是完成、还在跑、失败还是没查。用说话的方式写每行：「搜索慢是因为缺索引」，不是「搜索审查：完成」或「慢搜索：缺索引」。提到途中发现并修好的 bug。每行单独读都成立。还在等用户的不能标完成，行动项里说的不重复。总结下面最多三行，改变用户认知或必须做的事。再一行说你还能自己做的工作。

然后列行动项。问用户拥有的决定——合并、批准、选择——并给推荐。你会先做的步骤放进推荐。必须先做的也是，不可逆的也是。给出每个 PR、issue 或 agent 的编号或链接，在选项对比中也是。

形状跟决定走。单项决定一个 bullet：决定、你的推荐、对用户的影响、推荐的证据、风险，项名只出现一次。多个项共享一个决定时，决定和推荐写一次，然后每个项一个 bullet，最危险的在先：链接和名字、对用户的影响、推荐的证据、风险。某项的推荐只在和整体不同时才写。每项的风险即使低也要写，比如「低风险：只改了颜色」。等待的代价只在超过延迟时才说，比如有截止线或丢数据。

选项对比的决定，给出工作衡量过的每个选项：它给用户带来什么、代价是什么、有现状时给现状。这些代价就是风险，不再单独写风险行。上面的截图展示选项时，在每个截图下面写它的收益和代价。

## 视觉

视觉是图：截图、视频、Mermaid 图、图表工具出的图、生成的图。Markdown 表格不是视觉，即使有前后对比列。

当图比句子更容易理解时就画：设计或系统怎么工作、PR 栈或依赖链及每个 PR 的状态、修复前后对比、选项并排。**不画**：状态列表、行动项列表、没有连接的框。同一事实不在文字和图里重复。

每个图小到一眼能看完：最多六个框，每个框最多八个字。标签用大白话，不写「测试：通过」这种标签。一句话才能说清的事实放文字里，或者不放。

截图和视频在该变化可见时内嵌，不只给链接。如果可见变化没有截图，在总结行标「暂无截图」，并在那里说屏幕上改了什么。用已有事实画图：Mermaid 画连接关系，图表画数字。**不编数字，不画或生成你没截到的屏幕图。只链接存在的产物。**

## 迁移适配说明

- 纯提示词，无脚本与外部依赖。截图、视频、图像生成属于宿主可选能力，缺失时按正文只给文字和已有链接，不编造图。
- 正文提到的 PR、CI 运行、issue tracker 等共享记录，需要对应托管平台或工具（如 `git`、`gh`）的访问权限；不可用时该项写「未知」，不推测。
- 未针对特定宿主或模型实测本 skill 的输出效果。
