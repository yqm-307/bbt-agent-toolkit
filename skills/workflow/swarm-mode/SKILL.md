# 蜂群工作模式

主会话负责分工和最终答案，worker 只交付自己负责的那一片。判断要不要派，看的是**哪些工作真的可以同时推进**，不是文件数。

## 先选最快的做法

- **一条确定性命令或一个本地脚本能做准，就直接做。** 抽取带固定标记的注释、精确替换字符串、合并 CSV，哪怕有几百个文件，也不需要模型逐个做。
- **大量条目需要逐项阅读或使用工具，但可以分别处理，就主动扇出。** 如按语义给工单分类、逐份核对接口迁移。先做一条定口径，再把剩下的按片并发交出去，不是一条配一个 worker。
- **要快速弄清一个系统，而多个问题能独立查证，也主动扇出。** 不必凑够几十条。例：看一个作业系统，可以让不同 worker 分查任务接入、执行和故障恢复。每片回答：入口在哪，谁调用谁，证据在哪，什么尚未确认。主会话把证据连成一条调用或依赖链，不拼接几篇介绍。
- 调一个依赖前一步结果的 bug、做一个贯穿多个模块的设计决定，留在主线。文件多不代表问题可拆；但多个只读片查看同一份源码并不冲突。

## 切片与派发

1. 列出应覆盖的条目或问题，为每片指定负责人、输入版本和验收条件。会写文件的任务按**实际写入范围**划界；同一文件有多个写入方时改为单一负责人。对照实验中，每组有独立、起始内容相同的可写副本。示范条目若已完成，不再派出。
2. **先派发，再深读。** 切出互不依赖、各自值得调查的片后，主会话的下一步是调用派发工具，而不是先把每片读完。一次交出本批就绪的片，主线保留跨片判断。并发按宿主限额、网关余量和已授权预算定；未知从小批起，限流则收窄。没有派发能力或路由被拒就如实说明，按现有权限降级，不拿线程或脚本冒充 worker。

   在 Hermes + OMH：按项目类别调用 `omh_delegate_route(action="set", category=…)`，确认路由可用后，同一轮调用 `delegate_task(tasks=[…])`，每片一个任务，不指定模型。`status` 只是查配置；只有派发回执才算已派，只有结果回来并核验才算完成。其他宿主用等价的原生派发工具。
3. 给 worker 的话要能单独执行：**只负责什么、不能动什么、怎样算完、交什么证据**。例如：「只读调度器，给出从入队到恢复的一条路径，附源码文件和符号；文档目标与实际实现分开。不要调查网络，不要改代码。」批处理用 `条目 ID | 状态 | 结果或阻塞原因 | 证据`；单条卡住，接着做下一条。大产物写独占位置，回传摘要与位置。

## 收回结果

- 对照最初清单核对缺失、重复和越界。能精确校验的就全量校验（集合、次数、差异）；需要判断的，抽查来源，优先核实最影响结论的项。进程退出、worker 自报成功或写出文件，都不等于验收通过。
- 收到失败或截断先看留下了什么，保留已验证部分。只在原因已处理且重跑不会重复写时补派缺口；仍拿不到证据就标明缺口。收到完成事件再汇合，不轮询。需要全量时，缺一片就不报全量完成。
- 交付用户要的东西：批处理给合并结果和覆盖数；调研给一个全貌、可追溯的关键关系和未知项。不贴 worker 的发言记录。没有可比的串行基线和计时，就不报提速倍数。

**入口与验证**：在能派发并回收并行子任务的宿主加载 `swarm-mode`；子任务权限、限额与项目门禁沿用宿主。本 skill 不安装运行时或调用外部 API。[评测用例](evals/evals.json) 分别检验脚本直做、独立调查扇出和单链调试不扇出。跨宿主行为须在相应宿主实测。

评测或自测「是否真的会派发」时，执行者必须是主会话：子代理的工具集里没有派发能力，用它跑只会得到假阴性，把「没派」误当成 skill 没生效。

设计参考：[Google Antigravity `/swarm`](https://antigravity.google/docs/swarm) 的不冲突分工；[pstack `/swarm`](https://github.com/cursor/plugins/blob/main/pstack/skills/swarm/SKILL.md) 的切片覆盖与缺口处理。
