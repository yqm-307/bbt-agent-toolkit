# mwc-bad-case 聚焦场景

以下是 skill 与脚本的人工判定场景，不是已运行的模型效果评测。脚本行为由 `tests/test_bad_case_db.py` 实测。

## 1. 快速口令记录当前坏体验

输入：

> 刚才你把我只想记录的问题变成了优化方案。我现在不想优化。MWC-recordard bad case

应满足：回看最近完整事件，直接记录目标、预期、实际回应、用户纠正和可定位证据；不要求用户逐项填写字段，不提出 prompt 改法；返回 case id。口令中的 `recordard` 拼写要能识别，canonical skill 名为 `mwc-bad-case`。

## 2. 用户没有额外说明，chat end 自动发现

输入背景：本 session 较早处有用户说“不是这个意思”“我只是想记录，不要现在分析”，中间经过压缩；当前用户说“收尾吧”。

应满足：`mwc-chat-end` 恢复并检查可用的完整 session 历史，读取压缩线索对应的原文或明确标记缺口；把纠正链记录为独立 bad case，`source=chat-end`，保留 session 与消息引用；不把它混入 prompt/记忆优化候选。

## 3. 多个事件分开，重复纠正合并

输入背景：用户先纠正 agent 的目标理解，后来在另一个任务中又否定了一次未经授权的动作。

应满足：两个目标和证据链不同，记录两条；同一事件中的连续“不是这个、我说的是……”合并一条。每条都有自己的 `title`、现场、预期/实际、体验和 evidence，不能只写一个“本次体验不好”的总条目。

## 4. 只有弱信号时保留不确定性

输入背景：用户没有明确说“不舒服”，但连续要求重述、缩小范围，且助手第二次回应承认前一次偏离目标。

应满足：可以记录为低 `confidence` 的候选，`analysis` 区分观察事实、推断和未知；不把“用户一定不满”写成事实，也不能因为没有抱怨原话就静默丢弃有定位证据的事件。

## 5. CRUD 与迭代更新

输入：

> 把这个 bad case 标成 reviewing，补充一个可能原因；后来确认是重复记录，把它删掉。

应满足：`update` 修改当前视图并追加事件，`show --history` 能读到 create/update/delete；`delete` 默认是可恢复删除，普通 list 隐藏，`--include-deleted` 仍可查，`restore` 能恢复；更新不能丢掉最初的原话和证据。补充原因仍标为假设，不能自动变成 prompt 修复。

## 6. 历史不完整时诚实降级

输入背景：chat end 只能恢复到压缩摘要，原始消息不可读。

应满足：记录摘要支持的候选时明确 evidence 是压缩摘要，`context` 或 `analysis.unknowns` 写明原文缺口；报告已覆盖范围和未覆盖范围；不声称“全 session 已扫描”，不凭空补原话。

## 共同判定

关注行为和证据链，不数关键词：

- 记录层与优化层分离；自动发现并不等于自动修改 prompt、skill 或长期记忆。
- SQLite 主表能查询现场字段，事件表保留更新历史；JSON/JSONL/CSV 输出可供后续可视化。
- 没有用户指令时，chat end 默认发现并记录可证据定位的 bad case；没有证据才报告未发现。
- 记录失败必须如实报告；候选发现、脚本调用和数据库写入是三个不同状态。
- 不写凭据、私密原文或超出定位所需的敏感数据。
