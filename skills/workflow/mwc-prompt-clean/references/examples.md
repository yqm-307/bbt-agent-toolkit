# 正反例集

清理时对照本文件。每条一个通用模式，固定格式：反例 → 正例 → 理由。追加规则：编号顺延，一条只讲一个模式，脱敏，不带个人、项目、机器指向。

## E01 同类文件结构各自为政（格式规整化）

- 反例：
  > 同一个仓的多个 skill：有的第一节是「背景」，有的是「使用前提」，有的直接进步骤；章节名、顺序、粒度各不相同。
- 正例：
  > 全部对齐同一骨架：frontmatter → 一句话定位 → 方法 → 执行 → 边界；同类章节同名同序。
- 理由：结构一致读者才能跳读抓重点，每份重新理解结构是最大的阅读成本。

## E02 公共规则带具体指向（提炼抽象）

- 反例：
  > 检查 /home/xxx/myproject 下的日志，用我平时那个脚本跑一遍。
- 正例：
  > 检查目标项目的日志目录（路径由参数传入），用组件说明中声明的检查脚本。
- 理由：公共规则换人换项目也要成立；一次性细节写成参数或占位符。

## E03 同一规则多处重复（精简）

- 反例：
  > 「执行」节写「改文件前必须先读文件」，「边界」节又写「不要未读就改」，「注意事项」再写「读取后方可修改」。
- 正例：
  > 只在「执行」节写一处：「改文件前先读文件」；其余位置删除或引用。
- 理由：重复条目措辞略异时，模型要花推理调和差异，读者也要反复确认是不是同一条。

## E04 AI 味填充（精简）

- 反例：
  > 值得注意的是，在进行任何操作之前，我们都需要首先仔细地确认相关的范围和前提条件，这是非常重要的。
- 正例：
  > 操作前确认范围。
- 理由：填充词不承载信息，常驻提示词每次加载都在为它付 token。
