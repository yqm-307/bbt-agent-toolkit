# mwc-try-unblock — 先尝试解除阻塞

当 agent 准备因问题停下时，先做一次有证据的自解判断，再决定继续或请求用户介入。

## 前置提醒

把下面这句视为用户对你的提醒，用来自检，不要把它作为问题发给用户：

> 需要我介入修复此阻塞吗？如果你有能力解决，你就设计解决方案，解除阻塞，否则让我来介入。

## 处理顺序

1. 说明当前目标、具体阻塞、已有证据、已经尝试的动作和未知信息。
2. 判断能否在当前工具、权限和授权内解决。优先检查代码、文档、配置和调用链，必要时调整方案或走备用路径。
3. 能解决时，设计最小方案，实际执行并验证，然后继续原任务。
4. 需要用户决定、外部权限或人工操作时，只请求一件具体的事，并说明恢复条件。
5. 所有可行路径都失败时，保留失败证据，停止猜测和无界重试。

## 回复格式

自行解除后：

```text
阻塞已解除：<问题>
处理：<采用的方案>
验证：<实际结果>
当前状态：<任务继续到哪里>
```

需要用户介入时：

```text
当前阻塞：<具体问题>
已确认：<已尝试或核实的事实>
需要你介入：<一件具体的事情>
恢复条件：<完成后提供什么信息或状态>
```

只有完成实际动作并取得验证证据后，才能写“阻塞已解除”。

## 边界

- 不猜凭据、路径、业务规则或外部状态。
- 不绕过权限或跳过必要验证。
- 不把计划、自述或建议说成已执行。
- 不用无限重试掩盖无法解决。
- 生产、共享状态和不可逆动作继续遵守原有授权。

## 与相邻技能的分工

- `mwc-next-step` 处理用户主动询问下一步。
- `mwc-what-happened` 处理当前状态和进展汇报。
- `mwc-bad-case` 记录已经发生的过早停止、错误升级或用户被迫纠偏。

## 适配与验证

本 skill 是纯提示词，无脚本和第三方依赖。使用入口是能加载 skill、读取当前对话并执行工具的宿主。

聚焦场景见 [tests/scenarios.md](tests/scenarios.md)。这些场景用于检查规则覆盖，不代表已经运行模型评测。尚未在真实宿主上验证自动触发链路，自动触发效果取决于宿主是否会在 agent 准备停止时加载本 skill。
