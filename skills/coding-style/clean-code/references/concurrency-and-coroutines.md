# 并发、异步与协程

## 同步保护不变量

每份共享可变数据说明谁访问、由哪把锁或哪种原子协议保护。多个字段共同维持不变量时，分别改成 atomic 不保证整体一致；默认用清楚的锁，只有有证据的瓶颈才考虑无锁。
`volatile` 不建立 happens-before，不消除数据竞争。版本号原子或读取后重试，也不能补救普通 payload 的并发读写；release/acquire 只在所有冲突访问确实被 happens-before 排序时有效，不给反复覆写的非原子载荷自动免责。历史存在不构成豁免；修复前追踪读写路径，不机械替换类型。

系统锁保护短临界区；普通业务代码不要持线程互斥锁调用可能挂起、阻塞或重入的未知代码。潜在后果包括死锁、饥饿、恢复线程改变后的非法解锁，不是每次调用必然“全进程卡死”。
底层同步原语若有专门的锁交接协议，核对并验证协议，不从通用风格直接改写交接顺序。

## 等待与通知

通用目标是：完成事件不会丢、同一工作不会重复恢复、状态与寿命在发布前准备好。不是所有实现都“先挂起再注册”；注册、准备等待、复查条件、发布与恢复的原子性取决于 API。
条件变量用谓词等待；事件循环、协程用框架提供的等待原语，不凭想象编造 YieldThen 等接口。取消、超时、正常完成竞争应有明确的唯一完成与清理责任。

## 回调与线程局部

捕获形式不等于寿命证明。回调可能同步触发、重入或晚到，销毁/取消前应确保没有后续访问，或用框架认可的延寿机制。
TLS 对象寿命通常到所属线程结束，指针跨线程不必然立即悬空，但要检查寿命、线程亲和性与同步。协程迁移线程后，不把之前缓存的线程局部上下文当成当前上下文。

## 协程与关机

Google 允许使用项目认可的 C++20 协程库，不鼓励业务代码自造 promise/awaitable。不能因某仓使用栈式协程而禁止所有项目的 co_await。
业务代码遵循已有框架；开发协程库本身需要专项设计和寿命/竞争验证，不套业务调用限制。
禁止在另一执行流仍使用对象或运行栈时直接销毁它。停止投递、取消、等待在途任务与释放依赖的顺序依目标契约验证，不在本 skill 固化一个调度器实现。

## 静态存储期

Google 要求静态存储期对象平凡析构，包含函数局部 static；局部 static 允许动态初始化，不意味着允许任意析构。非平凡全局对象和跨翻译单元依赖容易造成启动/退出阶段访问已失效对象。
优先将服务状态交给显式寿命的拥有者。故意不析构属于需要说明的特殊设计，不作为默认修法。对已有对象区分风格偏差与真实退出期竞态，不给予“一律不报”的豁免。
