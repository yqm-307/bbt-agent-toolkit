# Clean Code 判断准则

按 `SKILL.md` 的问题入口读取相关章节；这些是降低理解成本的经验，不是所有语言的硬规则。正反例及边界用例见 [examples.md](examples.md)。

<a id="命名与接口"></a>
## 命名与接口

- 用已有领域术语，同一概念同一词；名字匹配作用域，单位、端点和副作用可辨认。`Data`、`Info`、`Manager` 不是禁词，但不能掩盖不清楚的职责；读取操作不能悄悄创建、消费或持久化。
- 调用点有歧义时，优先现成类型、枚举、结果结构、具名参数或常量；不为每个值包类型，不用任意字符串替代有限选项。
- 参数多或布尔标志只是检查线索，不是缺陷。明确布尔属性可保留；已发布接口不能因审美变更，也不能仅凭仓内无调用判定可删。

<a id="流程与复用"></a>
## 流程与复用

- 一个函数表达一个逻辑操作，按语义而非行数划分。早退仅在保持全部可观察行为时采用：错误集合、副作用次数与顺序（释放资源、日志、审计、计数、回调）及公共失败语义都不变。
- 提取函数须命名独立概念、隐藏细节或统一同一规则；只转发参数、增加跳转无益。保留原有求值条件与次数，不能把条件读取、调用或参数求值提前为无条件执行；清楚的局部判断不必建 helper。
- 函数提取与重复治理的设计依据见 [职责与抽象](design-principles.md)：先核同一知识/不变量，再判断边界与总成本；不按语法相似自动合并。
- 不设函数行数或参数数量硬阈值，不强制 getter/setter、接口、设计模式或 DRY；不为套规则新增框架、强制 TDD 或顺手清理周边。
- 不以整洁为由将错误码改成异常、借用改成复制，或删必要空值检查。行为保持优先于审美，等价排版与个人偏好不算缺陷。

<a id="注释"></a>
## 注释

- 含混能用准确命名或直接写法消除时，先改善代码；删逐行翻译、装饰性分隔和开发流水账，不为删注释制造 helper。
- 保留契约、单位/边界、不变量、所有权、并发时序、复杂算法摘要和非显然取舍。推导成本很高的信息也值得说明，不机械要求“只能 WHY”。
- 一处事实尽量一处说明，附近引用而非复制；代码变更同步更新注释。法律声明、许可证和有追踪价值的 Issue/TODO 链接不当噪声删除。
- 注释与代码冲突先核契约和测试，不用实现自动覆盖意图；注释掉的旧实现须确认废弃且在授权范围才移除。示例、法律文本与解释性伪代码不是死代码。
