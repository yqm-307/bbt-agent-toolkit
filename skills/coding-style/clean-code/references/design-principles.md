# 职责与抽象：把复杂度放在正确的位置

用于局部设计、重构与评审；不是让所有项目采用某一种运行时架构。表达细节见 [principles.md](principles.md)，示例见 [examples.md](examples.md)。正确性、安全、契约优先，优化不能删掉这些保证。

## 先减职责，再简实现

模块难以理解时，先区分问题本身与额外承诺：它是否兼管了别人的生命周期、策略、兼容或资源？只有需求确实不需要、消费者已核对且变更获授权，才缩小承诺。删除需求、错误路径或安全检查不算简化。

复杂度由拥有必要信息与控制能力的层承担；底层提供可组合原语，上层负责自己的业务策略。不要为方便调用者让底层承诺它无法兑现的行为。不是固定套用“业务/资源/调度”三层：边界由真实消费者和变化原因决定。

## 抽象同一规则，不抽象偶然相似

提取前问：

1. **稳定语义能命名吗？** 多处是否必须随同一知识或不变量改变，而非只长得像？
2. **消费者少知道细节了吗？** 是否仍保有完成真实工作的必要控制，不必频繁穿透封装？
3. **总成本下降了吗？** 一起看调用点、实现、错误处理、测试与调试，而非只数重复行。

任一项没有依据，先保留直接写法或修局部命名。一个真实消费者也可以需要清晰语义边界；多个调用点也可能只是偶然相似，不设“几次重复才能提取”的门槛。公共 API 变更另核兼容与授权。

## 简单接口，完整协议

接口说清“做什么”和调用者需要遵守的前提；复杂机制集中到负责它的内部，而不是把所有实现暴露出去。跨线程或异步工作必须能回答：

- 谁拥有对象，谁只是借用，何时转移责任？
- 何时发布有效状态，失败后保留什么？
- 谁有权完成和清理；取消、超时或重复通知怎样仲裁？

同步代码没有这些竞争，就不要强加状态机、代际、注册表或取消协议。确有竞争才用最小充分机制；引用计数、原子字段或日志本身不是完整协议。

## 复用优先，扩展有具体理由

先复用既有代码、标准能力和已经采用的成熟依赖，再写最小适配。直接调用现成后端足够时，不添加 Port/Factory/Manager 链；为稳定边界或真实替换需求设置接口，不为想象中的后端数量建框架。

通用实现与资源治理不一定要集中在同一个类。可组合的小能力优于全包框架，但不为“解耦”增加只有转发的 wrapper。

## 有限方案可以，隐含限制不行

单实现、固定容量、串行执行等方案满足当前需求即可。说明适用范围、达到天花板时的失败行为和升级信号；不要把“以后优化”当说明。代码需要留说明时沿用项目注释习惯，有明确简化上限可写 `ponytail:` 注释，不对普通代码机械加标签。

优化先获得真实瓶颈或正确性缺口。锁、位打包、模板、继承都只是工具：短小不等于简单，lock-free 不自动更快，现代特性不自动更清楚。诊断容许陈旧也不授权数据竞争。

## 边界与例外

- 少封装不等于少校验；机械重复可删，信任边界不能删。
- 显式机制不等于业务调用者必须看懂底层所有细节；必要控制与实现泄漏要分开。
- 简单类可以直接构造，复杂有效性建立可用工厂；不一律禁止或要求工厂。
- 观测成本、特殊生命周期或平台限制需要证据和说明，不把某仓历史写法变成通用规范。
- 已证实的泄漏、悬空和数据竞争不能因“跟周围风格”保留；修复仍遵守授权与验收边界。
