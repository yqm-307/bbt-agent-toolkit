# 最小变更与克制建设

用于判断实现是否承担了不必要的承诺，配合本 skill 的职责、抽象与行为保护原则使用；不接管任务编排、审查流程或输出风格。

## 先复用，再添加

在理解需求与真实调用关系后，依次考虑：不需要新增能力、已有实现、标准库、平台原生能力、已安装依赖、直接实现。停在第一个满足明确需求和边界的方案，不为走阶梯做无界调查。

- 少量重复未必需要抽象；稳定的语义边界或独立客户端已明确时，也不必等重复出现才设计接口。
- 减少文件、依赖和跳转是手段，不以最少行数牺牲可读性、求值语义、错误处理或测试。
- 共享根因在共同位置修复；先核调用方的真实差异，不因表面相似强行合并。
- 刻意采用有上限的朴素算法时，在实际代码注释中说明适用边界和何时升级，不额外引入统一标记协议。

## 不能省的部分

信任边界校验、防数据丢失、安全、无障碍、明确需求与必要行为检查不能为“小 diff”删掉。非平凡逻辑保留能区分关键错误的可运行检查；简单措辞不机械增加框架或逐函数样板。
