# 代码测试用例设计

目标是把需求中的行为和失效风险映射到可执行的测试，而不是列出一张“常见测试技巧”清单后逐项套用。本 skill 负责**用例选择与设计**；只跑现有测试、发布放行和独立审查遵循项目现行规则。

## 先判断是否适用

- 适用于新增行为、缺陷修复、回归遗漏、覆盖缺口，以及“这组测试是否真的能抓住问题”的检查。
- 如果用户只要求运行已经确定的测试命令，不重新设计用例；如果改动只有格式、文档或无行为配置，使用相应的解析、构建或 smoke 检查，不强迫发明业务案例。
- 测试层级优先选能观察到风险的**最低层级**：纯逻辑用单元测试，序列化／公共 API 用契约测试，模块边界和外部依赖用集成测试，真实浏览器输入／渲染／轮询用浏览器或端到端测试；低层级隐藏了问题时再上移。并发、异步和分布式行为先在可控的集成环境验证交错与终态，压力测试另按性能契约设计。

## 输入与前置

- 先读取需求或已确认的行为契约、受影响代码及调用者、现有测试入口与可控环境。把**预期行为的来源**与当前实现分开；不能把代码现状直接当正确预期。
- 标出输入域、输出和副作用、错误语义、状态变化、依赖边界，以及已知回归。区分「已规定非法输入」与「未规定的处理细节」：若契约要求正整数且非法输入返回错误，非整数属于已知非法类；错误是返回值还是异常若未说明，才标记为未知。关键预期缺失时先向契约来源查证，仍未知就标记待确认，不编造断言。
- 确认测试不会意外修改共享／生产数据。未经授权，不为“验证”执行生产写入、故障注入或安装测试工具。

## 选择并设计

1. 写最小行为清单：每条包含前置条件、动作、可观察结果、断言位置和契约依据；同时标出风险所在的测试层级。优先复用现有回归用例，不重复造框架。
2. 按 [测试方法目录与条件决策表](references/methods.md) 选择方法：先覆盖有效／无效类和关键边界，再按条件叠加规则组合、状态、交互、故障等方法。决策表是**候选生成器**，不是必须执行全部方法的门禁。
3. 让每个案例都能区分至少一种具体错误。给出输入或事件序列、预期输出／状态／副作用及断言位置，并把该输入代入正确与错误条件核对：若两者结果相同，就删掉“可检出该错误”的说法或改选输入。按具体输入／事件序列计数，`0` 和 `2.5` 是两例，不可合并为一例绕过预算。
4. 先覆盖契约关键分支，再补恢复、重复、并发和兼容路径；预算紧时保留判别力最高的案例，未选的高相关方法写明未覆盖原因。不要用用例数、方法数或行覆盖率代替风险覆盖。
5. 优先检查能观察到真实行为的路径。mock 只隔离不可控边界；对 mock 的调用断言只能证明接线，不能单独证明业务行为。固定时间、随机源、重试和外部响应，避免案例依赖偶然顺序。
6. 若用户要求执行且环境可用，运行选中的案例，记录目标版本、命令、退出状态和关键结果。失败先区分实现缺陷、测试断言错误和环境故障；修复后重跑对应回归。环境不可用时交付案例草案并标为**未验证**，不写“通过”。
7. 当每个已知高风险都有至少一个能区分错误的案例，或剩余风险已明确标为未知／未覆盖，并且新增案例不再改变当前结论时停止。

## 正反例

- **正例**：契约是库存 `stock >= requested` 才允许下单。`stock=4, requested=4` 能区分正确实现与误写成 `stock > requested` 的实现；再用 `requested=5` 覆盖拒绝路径。
- **反例**：只用 `stock=4, requested=5` 声称覆盖 `>=` 边界。正确实现和 `>` 实现都会拒绝，这个输入不能证明边界测试有效。
- **正例**：异步任务测试同时断言终态、超时／失败语义和重试后的副作用次数；这能发现“返回成功但重复写入”或“超时后仍修改状态”。
- **反例**：只断言 HTTP 200、mock 被调用或“最终成功”，却不检查状态、错误传播和副作用；这类测试可能全绿但没有保护行为。

## 最小交付

按行为给出「契约依据 → 风险／测试层级 → 选用方法 → 输入或事件序列 → 预期及断言 → 能区分的错误 → 实跑证据或未验证原因」，单独列出未知预期、未覆盖的高风险路径和不适用的方法。测试是否足以支撑发布、是否还需独立审查，遵循仓库既有门禁，不由本 skill 决定。
