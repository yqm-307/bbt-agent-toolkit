# Prompt Denoise — 提示词降噪

降噪的目标是让每条规则只有一种读法，提高有效信息密度，不是压字数。判断标准是模型行为：会让模型犹豫、乱猜、不必要地停下或用力过猛的句子都是噪音。

## 为什么值得做

- 指令越被严格遵循，矛盾和含糊的伤害越大：模型会花推理去调和矛盾，而不是随便挑一条。OpenAI 的 [GPT-5 prompting guide](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide) 举了预约系统的例子，并说早期用户审查提示词库、删掉矛盾后效果明显变好。
- 为旧模型写的催促在新模型上会过度触发：Anthropic 的 [prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) 指出 Opus 4.5/4.6 等新模型对系统提示词更敏感，原本为防漏触发写的强硬措辞可能导致过度触发，建议把「CRITICAL: You MUST use this tool when...」改成普通的「Use this tool when...」。
- 规则只增不减：每次纠错追加一条，历史补丁、重复和过期引用会累积，常驻文件每次加载都在付这笔成本。

## 何时用，何时不用

- 用：常驻提示词或 skill 正文需要整体降噪；有可观察症状（频繁确认、忽略规则、过度设计、行为前后不一）；模型换代或项目大改后的定期体检。
- 不用：只改一两处措辞；整仓体量、引用和重复的巡检（交给仓库自己的健康度工具）；从零写新提示词。

## 六类噪音

| 类型 | 一句话 | 典型改法 |
|---|---|---|
| 冲突 | 两条规则给出不同做法 | 写明优先级或例外 |
| 重复 | 同一规则多处出现、措辞略异 | 只留一处正文，别处引用 |
| 模糊触发 | 触发条件用未定义的词 | 换成可判断的条件，附一个例子 |
| 过宽过强 | 绝对化、无范围，或范围实际覆盖一切 | 加范围，写明何时可以不做 |
| 过期 | 引用的文件、命令、事实已不符合现状 | 对照现状修正或删除 |
| 放错层 | 常驻层装了按需内容，或写了能从仓库推断的事实 | 挪到 skill 或文档，常驻处留入口 |

识别信号、正反例和不要误伤的情况见 [references/noise-taxonomy.md](references/noise-taxonomy.md)。

## 流程

### 1. 定范围与症状（主 agent）

- 通读目标文件一次，确认真源：软链、投影或生成产物只审它的源文件。
- 列出参与判断的文件：目标文件，加上它要求必读、且可能与之冲突的少数文件。直接点名，不要整棵文档树拉进来。
- 写下症状（可观察的行为）。没有症状就写「定期体检」，此时只报高置信问题。
- 记下目标文件受哪些门禁保护（如受保护路径、独立审查要求），第 5 步要用。

### 2. 机械提取（脚本）

```bash
S=scripts/extract_inventory.py   # 相对本 skill 目录
OUT=<仓外临时目录>
python3 "$S" <文件...> --root <仓库根> --out "$OUT/inventory.md"
python3 "$S" <文件...> --root <仓库根> --flagged-only --out "$OUT/flagged.md"
```

脚本把文件拆成带编号的句子（如 `F1-L12.2`），并一次做完：引用路径是否存在、绝对化/授权/审查/模糊措辞标记、跨文件近似重复。先读摘要。标记只是候选，不是结论；清单含原文，放仓外临时目录，不入库。摘要提示清单过大时，回到第 1 步缩小文件范围。切分与标记是启发式的：行内代码里的分号、`e.g.` 会被断句，多行 HTML 注释会被当正文，嵌套代码围栏可能错位。

### 3. 分路分析（子代理并行）

三路互不依赖，并行派发；每路只拿清单路径、本路检查表、症状和输出格式，不拿会话历史：

| 路 | 读什么 | 找什么 |
|---|---|---|
| A 冲突与重复 | `inventory.md` | 冲突、重复 |
| B 触发与强度 | `flagged.md`，需要上下文时按编号回查 `inventory.md` | 模糊触发、过宽过强 |
| C 现状与分层 | `inventory.md` + 缺失引用清单，可只读打开仓库核对具体事实 | 过期、放错层 |

派发包原文和统一的发现格式见 [references/lane-briefs.md](references/lane-briefs.md)。目标不足约 80 句时不派子代理，主 agent 按三路顺序自己做；宿主不支持子代理时同样顺序做。

### 4. 合并核对（主 agent）

- 先机械核对：`python3 "$S" <文件...> --root <仓库根> --verify "$OUT/lane-X.jsonl"`，编号不存在、引文对不上或格式不对的发现先改正或剔除，子代理自述不算。`--verify` 会按传入参数重建清单再核对：文件列表与顺序、`--root`、`--follow` 必须与第 2 步完全一致，第 1–4 步之间不要改动目标文件。
- A 路与 B 路常命中同一句（冲突往往落在确认类措辞上），按编号合并成一条，保留更具体的拟改文本。
- 每条写清：类型、编号与原句、会怎样改变 agent 行为、拟改文本、置信度。
- 有意设置的保障标「保留」；任何会放宽权限或减少确认的改动单独列出，用 P 编号，不进主表，不随「全采纳」生效。
- 按对行为的影响排序，用 [references/lane-briefs.md](references/lane-briefs.md) 末尾的报告模板输出。

### 5. 人工确认后落地

- 交报告后停下，由用户采纳；P 编号条目须逐条点名。未确认前不改目标文件。
- 只改采纳项，做最小定点修改。
- 改完重跑脚本：已处理的缺失引用和近似重复应消失，新增标记要能解释。
- 受保护文件或规则的实质变更，按所在仓库的独立审查与提交门禁走；选择本 skill 不构成跳过门禁的授权。
- 症状驱动的降噪建议做行为验证：挑 2–3 个能复现症状的典型任务，改前改后各跑一次对比。没做就在交付里写「未做行为验证」。

## 改动守则

- 不为缩短删边界约束：安全、权限、不可逆操作的规则只澄清范围，不删除。
- 冲突给优先级或例外；只有一条已过期时才删它。
- 模糊词换成可判断的条件；绝对化语气改成带范围的普通陈述，并写出何时可以不做。
- 引用以现状为准：先查文件和命令，再改字。
- 挪走的内容在常驻处留一句「何时去读哪里」。

## 依赖与验证

- 方法本身不绑定宿主，完整流程仅在 Hermes 中实跑过；子代理并行是可选增强。
- 脚本：Python 3.10+（实测 3.11、3.14），只用标准库；只读，除 `--out` 指定的文件外不写任何东西，不联网。
- 首次使用验证：在本 skill 目录运行 `python3 -m unittest discover -s tests`。
- 未验证：macOS、Windows、Python 3.10/3.12/3.13；其他宿主的子代理派发；改前改后的行为对比。

## 边界

- 第 1–4 步只读，不修改目标文件。
- 不授权提交、推送或修改运行配置。
- 不替代仓库自己的 lint、审查与提交门禁。
