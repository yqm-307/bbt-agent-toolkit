# 噪音分类：识别、改法与误伤

每类给出定义、识别信号（含脚本标记）、正反例和不要误伤的情况。例子来自真实降噪，已去掉项目细节。

## 1. 冲突

两条规则对同一情形给出不同做法，模型只能猜哪条优先。

- 信号：同一主题（授权、审查、构建、测试、提交、输出格式）出现在多个标题或文件下；数字、条件或主体不一致。
- 例：常驻文件写「并发相关改动须独立审查」，流程文档写「独立审查按风险执行」。
- 改法：写明优先级或例外，如「下列路径须独立审查，其余按风险自审；本仓文档另列的类别从其规定」。
- 不要误伤：上下级文件故意更严（如子目录规则收紧全局规则）不算冲突，只要有一句说明哪级优先。

## 2. 重复

同一条规则在多处出现，措辞略有差异，读者无法判断以哪处为准，修改时也容易只改一处。

- 信号：脚本的近似重复对；同主题清单出现两次（如两份「先确认」清单）。
- 例：一处写「构建并发固定为 2」，另一处的示例命令用 `nproc/4`。
- 改法：只留一处完整正文，其他地方用一句引用；示例命令也改成引用后的口径。
- 不要误伤：为了让多个仓库各自独立可用而有意保持逐字相同的公共段，只要有同步约定就不算噪音。

## 3. 模糊触发

触发条件用了没有定义的词，模型要么停下来问，要么自己猜。

- 信号：`vague` 标记（适当、尽量、必要时、关键、简单、非 trivial 等），以及没有定义的角色或对象（「负责人」「相关方」）。
- 例：「非 trivial 变更先走方案共识」，全仓没有说什么算 trivial。
- 改法：换成能判断的条件，最好附一个例子，如「改公共 API 或契约、且 Issue 里还没有共识时，先出方案」。
- 不要误伤：留给模型判断的空间是有意的（如「按风险选择验证强度」）且附了判据时，不必硬改成规则。

## 4. 过宽过强

绝对化、没有范围，或名义上有范围、实际几乎覆盖一切，导致常规工作也要停下或过度执行。

- 信号：`unscoped_absolute` 标记；`gate` 标记集中在常规动作上；全大写或「必须」「CRITICAL」类强调。
- 例：「有疑问先问」不带条件；在协程库里写「并发关键改动须独立审查」等于全部审查。
- 改法：加范围，并写出可以不做的情况，如「只在疑问会改变做法、且自己查不到时才问」。强调语气改成普通陈述并说明原因。
- 不要误伤：安全、凭据、生产、不可逆操作的硬边界可以保持绝对化，只澄清范围。

## 5. 过期

引用的文件、目录、命令、版本或事实已不符合现状，模型会照抄错误内容。

- 信号：脚本的缺失引用；代码块里的命令与常驻规则口径不一致；写死的版本号、日期、数量。
- 例：引用了不存在的目录；示例命令用了未定义的变量，展开后等于不限并发。
- 改法：对照现状修正或删除；被常驻规则约束的命令，在所有可直接照抄的位置都要改。
- 不要误伤：明确标注为历史记录或某次实测结果的句子，保留原文。跨仓引用在本仓查不到不等于过期，需要到对方仓核对。

## 6. 放错层

常驻层装了按需才用的内容，或写了能从仓库直接推断的事实，稀释注意力。

- 信号：长流程、专项知识、一次性补丁、事故经过、版本沿革出现在常驻文件里；语言、框架、目录这类配置文件里就有的事实。
- 例：常驻文件里写完整的发布步骤和十几条命令。
- 改法：挪到 skill 或文档，常驻处只留一句「做 X 时先读 Y」。
- 不要误伤：缺失就会普遍出错、越权或破坏安全的内容应该常驻，即使它看起来像细节。
