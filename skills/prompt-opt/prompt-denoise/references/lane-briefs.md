# 分路派发包与报告模板

主 agent 按下面的模板填好 `<...>` 后派发。三路互不依赖，一次并行派出。

## 共同部分（每路都带）

```text
你在做提示词降噪的一路分析。除写本路发现文件外只读，不修改其他文件，不做 git 操作。

输入：
- 清单：<inventory.md 绝对路径>（B 路另有 <flagged.md 绝对路径>）
- 症状：<可观察行为；没有则写「定期体检，只报高置信问题」>
- 仓库根：<路径>（只有 C 路需要打开仓库核对具体事实）

引用一律用清单里的句子编号（如 F1-L12.2），ids 只列清单里真实存在的编号，evidence 里引用别的句子也用编号。不要通读清单之外的文件，不要提议整体重写。
有意设置的安全、权限、不可逆操作边界不算噪音；拿不准是否有意时标出，交主 agent 判断。

safeguard：被改的句子是有意设置的保障（安全、权限、审批、审查）时为 true。
widens_permission：提议会减少确认、缩小审查范围或放宽权限时为 true，即使你认为只是澄清原意。

每条发现写一行 JSON 到 <OUT>/lane-<本路>.jsonl，最终回复也原样给出这些行：
{"lane":"A|B|C","type":"冲突|重复|模糊触发|过宽过强|过期|放错层","ids":["F1-L12.2"],
 "quote":"原句，80 字以内","impact":"会怎样改变 agent 行为","proposal":"拟改文本",
 "safeguard":false,"widens_permission":false,"confidence":"high|medium|low","evidence":"判断依据"}

没有发现就输出 {"lane":"<本路>","none":true}。最多报 <N，默认 15> 条，按对行为的影响排序。
```

## A 路：冲突与重复

```text
检查表：
1. 先看清单的「近似重复」列表，逐对判断：一致（可合并）、不一致（冲突）、有意重复（如多仓公共段）。
2. 按主题横扫全清单：授权与确认、审查、构建与测试、提交与发布、输出格式、优先级声明。
   同一主题出现两处以上时，比较数字、条件、主体是否一致。
3. 冲突给出建议的优先级或例外写法；重复指明保留哪一处为正文。
```

## B 路：触发与强度

```text
检查表：
1. 读 flagged.md。对每条带 gate / unscoped_absolute / vague 标记的句子问：
   - agent 能否自己判断这条何时适用？不能 → 模糊触发。
   - 它会不会让常规工作也停下来确认或多做一步？会 → 过宽过强。
   - 名义范围是否实际覆盖几乎所有任务？是 → 过宽过强。
2. 需要上下文时，按编号回查 inventory.md 的同一标题下的句子。
3. 再扫一遍没有标记但用了未定义名词的句子（「负责人」「相关方」「关键路径」等）。
4. 区分有意保障与意外扩大的确认面。
```

## C 路：现状与分层

```text
检查表：
1. 逐条核对清单的「缺失引用」：确认真缺失、跨仓引用还是工具误报（如目录约定 `references/` 被当成引用）。
2. 看代码块里的命令和路径，是否与清单中常驻规则的口径一致（并发、目录、工具名、变量是否有定义）。
3. 找写死的版本、日期、数量、目录清单，只读打开仓库核对是否仍成立。
4. 找放错层的内容：长流程、专项知识、一次性补丁、事故经过、能从配置文件直接看出的事实。
   提议挪到哪里，常驻处留什么入口句。
```

## 报告模板（主 agent 合并后输出）

```markdown
# <目标文件> 降噪报告

结论：<一句话：发现几处、最影响行为的是哪类>。未修改任何文件。

范围：<文件与 sha256 前 12 位>；症状：<...>；分路：<A/B/C 是否派发、是否顺序执行>

## 建议修改（按影响排序）

| # | 类型 | 位置 | 原句 | 影响 | 拟改 | 置信度 |
|---|---|---|---|---|---|---|

## 会放宽权限或减少确认的改动（编号 P1、P2…，不计入「全采纳」）

| # | 类型 | 位置 | 原句 | 影响 | 拟改 | 置信度 |
|---|---|---|---|---|---|---|

## 有意保留，不改

## 已核对为误报

## 未覆盖
<没打开核对的事实、没做的行为验证等>

请回复「采纳 1,3」「全采纳」或「都不要」；「全采纳」只覆盖「建议修改」表，P 编号条目须逐条点名，如「采纳 P1」。
```
