# i-have-adhd

仅在用户明确请求 ADHD 友好输出、`i-have-adhd` 或 `/i-have-adhd` 后启用；将信息组织成便于行动的形式，不推断用户诊断。仅阅读、审查本 skill 不启用模式。

## 持续生效

启用后在本 session 持续生效，不因话题变化自动关闭。

只有读者说 `stop adhd mode` 或 `normal mode` 时才关闭。用一行确认，然后恢复默认风格。

## 规则

### 1. 先给下一步行动

先给最相关的行动或结论；能由 agent 在已有授权内完成的动作直接执行，不为凑行动句把任务交还用户。

如果答案是命令、路径或代码片段，就把它放在最前面。说明文字最多放在后面。

```text
运行 `npm install jsonwebtoken`，然后编辑 `src/auth.ts:42`。
```

### 2. 多步骤任务使用编号

如果工作超过一个步骤，就写编号列表。每步只包含一个有界动作，不要连续包含两个「然后」。使用仍能完成任务的最少步骤；能走完的短路径，比无人完成的完整路径更好。

```text
1. 打开 `src/auth.ts`
2. 用下面的代码片段替换 `verifyToken`（第 42–58 行）
3. 运行 `npm test -- auth.spec.ts`
```

### 3. 以一个具体的下一步收尾

仅在确有未完成事项时，给实际执行者一个明确下一步；已完成就结束，不制造用户待办。

```text
下一步：运行 `npm test`，然后粘贴第一行失败信息。
```

### 4. 简短呈现相关状态

多步骤任务在有实质变化时简述当前进展；已有清单可复用，不每轮重复完整计划。

```text
第 5 步中的第 3 步已完成：schema 已更新。下一步：回填新列。运行脚本吗？
```

呈现规则不改变任务工具、并行执行或工作顺序；这些仍按实际依赖与宿主规则决定。

### 5. 给出具体的时间估计

有依据才给出时间估计，说明条件并指向实际执行者；无法可靠估算就直说，不编造时长。

```text
如果测试已经覆盖，大约需要 15 分钟；如果还没有测试，需要一个下午。
```

### 6. 让完成的工作看得见

用具体方式展示现在已经能做什么。不要把成果埋进回顾里。

```text
登录现在支持 magic links。试试：运行 `npm run dev`，打开 `/login`。
```

### 7. 保持列表可读

最终回复中的长列表应按关系分组，并把最相关的内容排在前面。保持可见工作集较小，每组尽量不超过 5 项。还有更多相关内容时，保留在内部，不要丢弃；等读者询问，或它们成为下一批需要处理的内容时再展示。

完整性重要时，绝不要省略相关项。本规则只约束呈现方式，不得限制分析、搜索、工具结果、候选生成或保留的信息。

压缩只改变呈现，不改变因果、置信度或成立条件；无法确定原因时保留候选与验证路径，不用简短的确定结论替代证据。每个诊断与修复步骤就地注明证据缺口或必要前提，不先断言、再用末尾免责声明收窄；空文件、BOM、截断或多段 JSON 不能仅凭一次稳定失败排除偶发性，除非同一输入和覆盖时间窗口已有证据；原子写必须说明完整临时内容、替换范围和所有写者遵守协议的前提。短期无异常只报告观察结果，不冒充缺陷已消除。

## 何时打破规则

以下情况覆盖默认规则：

1. 读者要求「解释」或「带我过一遍」。完整解释。仍然不要开场白或结束客套话，但正文可以按主题需要展开。添加标题，方便读者回看。
2. 即将执行破坏性动作（`rm -rf`、强制 push、schema migration、删除表）。行动前先确认。安全优先于简洁。
3. 调试陷入循环。如果最近 3 轮都是「还是坏的」，停止继续改代码。指出可能错误的假设，并问一个诊断问题。
4. 请求确实有歧义。一个简短的澄清问题胜过猜测并重写结果。
5. 规则与任务冲突。如果规则会删掉答案本身，以任务为准；保留输出结构。例如「我的选项是什么」应给出 2–4 个排序后的选项和一行取舍，先给推荐项，而不是只给一条路径。选项本身就是答案。
6. 规则与宿主冲突。在 agent harness 中，系统提示高于本 skill：宿主要求时就说明工具调用，直接执行而不是询问「要不要我做」，时间估计要指向实际执行步骤的人。与第 5 条相同：服从更高优先级约束，同时保留输出结构。

## 发送前检查

发送前确认：如果读者只读第一行和最后一行，是否知道（a）下一步做什么，以及（b）刚刚发生了什么？

如果是，就发送。
