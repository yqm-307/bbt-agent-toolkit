# 测试用例设计职责

**何时读**：为新行为、缺陷、回归或覆盖缺口选择和设计用例，或精简、删除已有用例时。进入本文件前先读目标仓声明采用的共用原则和测试规范。只运行已经确定的测试命令时不重新设计测试。发布放行归项目门禁，不由用例数量决定。

本文件只负责“什么值得测、测什么行为、何时新增或删除”。测试层级和方法见[测试方法目录](test-methods.md)，开发中与合入时的运行范围见[按阶段运行测试](test-execution.md)，并发交错与生命周期责任见[并发与生命周期用例](concurrency-cases.md)。

## 1. 从契约而不是实现选例子

找到行为来源，列出输入、结果、状态、资源责任和对外副作用。先覆盖生命周期和失败风险；未知要求标成待确认，不从现有实现倒推规格。

每个关键用例至少写清：

```text
前置条件 → 动作/事件 → 可观察结果 → 断言 → 能抓住的错误实现
```

正例：契约规定 `stock >= requested`，使用 `stock=4, requested=4`，断言成功，能抓住误写成 `>` 的实现。

反例：只用 `requested=5` 测不足库存；正确实现和错误的 `>` 实现都会失败，测试无法区分它们。

预期结果来自契约或独立参考，不用被测逻辑生成；同时确认夹具确实触发了目标条件，目标错误出现时对应断言会失败。

正例：用协议文档里的固定样例核对编码字节；关闭回归先确认确有在途回调，再触发 Close。

反例：编码和解码共用同一个错误，靠“编码后再解码等于原值”照样通过；或者只调用了 Close，就声称验证了关闭期间的回调交错。

## 2. 选择能直接观察风险的层级

纯逻辑优先放单元测试，公开边界放契约测试，跨模块、真实线程/协程或外部依赖放集成测试。只有低层级看不到风险时才上移，不用大测试替代明确的局部断言。具体层级表和上移信号见[测试方法目录](test-methods.md)。

用例归属被验证契约的责任模块：下层语义在下层测，跨模块的组合由承担组合责任的模块测。上层只补自己新增的组合、接线和责任。

正例：容量拒绝策略在公开队列接口做契约测试，资源释放再用最小生命周期集成测试确认。

反例：为一个纯函数启动完整网络服务；或用 mock 调用次数通过来代替真实后端错误传播。

## 3. 先测边界和失败恢复

优先有效/无效输入、空值、最大容量、刚好边界、重复调用、取消、超时、异常、恢复和最终释放。涉及规则组合或状态变化时增加有意义的事件序列，不按“每个分支写一例”机械扩张。这份清单用来挑出与本次风险相关的情形，不是逐项补齐的任务。

正例：改一个同步、无状态的地址解析函数，只补空串、非法端口、端口刚好为 65535 和 65536 这几条输入边界。

反例：同一个函数也补上取消、超时、重入和关闭后调用的用例；这些情形在它的契约里根本不存在，用例只是在凑清单。

对每个用例代入一个具体错误实现。错误实现若仍能通过，调整输入、事件顺序或断言。覆盖率、通过数量和 mock 数量不能冒充区分力。用例按具体输入或事件序列计数，不能把不同案例塞进一个命名用例来绕过预算。

责任和副作用也要断言。必要时观察额度、任务、连接或借用资源是否归还，错误、未知结果和外部副作用是否可见，重试是否造成重复执行，Close 后迟到结果、回调和新调用如何处理，以及观测是否改变对象寿命或顺序。

正例：超时测试同时验证底层是否仍可能执行，以及调用者能否区分未知结果。

反例：看到 timeout 返回就断言远端未执行；看到 Close 返回就断言资源已经物理释放。

并发和时间相关的确定性做法见[并发与生命周期用例](concurrency-cases.md)，不要在本文件重复固定等待和交错协议。

## 4. 复用夹具但不伪造证据

控制时间、随机源和外部响应；mock 用于隔离边界。fake 能控制交错，但真实网络或外部系统的错误传播和资源行为仍需要对应集成证据。不要为了省时间把 fake 通过写成真实链路通过。

每条用例能单独运行，不依赖前一条留下的全局状态、端口或数据。夹具失败不能被当成业务通过，失败信息要指出是哪条行为不符合契约和实际值。

正例：每条用例独立初始化并在结束时清理，失败时报告“取消后额度未归还：期望 0，实际 1”。

反例：依赖上一条用例建好的连接，失败时只报“整个流程超时”；或者后端服务没启动，用例直接返回成功。

## 5. 什么时候加、加什么样的

命中下表只是触发覆盖检查，先看已有用例能否复用或补强，不自动新增。

| 情况 | 加什么 |
|---|---|
| 新建模块 | 按契约写最低限度的单元或契约用例，挑一两条能说明模块基本可用的打上项目冒烟标签 |
| 新增或改变公开契约 | 在该模块公开接口上加契约用例，断言新行为 |
| 修复真实缺陷 | 能区分根因的最小回归，优先在已有用例或数据表里补一条；一条覆盖不了不同责任路径时才再加 |
| 新增并发、取消、关闭或资源归还路径 | 能证明交错和收口的用例，详见并发专项 |

不因以下情况机械增加用例：

| 情况 | 原因 |
|---|---|
| 纯重构，且现有用例已覆盖受影响契约 | 已有断言不改就该通过；发现覆盖缺口时只补最小用例 |
| 下层模块已证明的语义 | 上层只测自己新增的组合和责任 |
| 能经公开接口低成本、确定地触发的内部行为 | 走公开接口测，不为测试扩大公共 API |
| 文档、注释、格式，以及不改变产物行为的构建调整 | 用链接、构建和格式检查；构建改动影响功能选择、依赖或测试注册时，验证对应产物 |
| 排障探针、一次性复现、诊断程序 | 结论留在仓外证据，确认的行为改写成回归用例 |
| 为覆盖率、通过数量或“每类情形都有一例” | 不增加区分力 |

所有候选用例，包括命中“该加”表的，都回答三个问题，三条都答得上才加：

- **有来源**：对应一条契约行为或一个真实出现过的缺陷。
- **有增量**：能抓住一个现有用例抓不住的具体错误实现。
- **层级对**：放在能证明它的最低层级。

变化探测用例指只固定契约没有承诺的内部结构或协作细节的用例：代码一重构就失败，行为错了却可能照样通过。契约要求的调用次数、顺序和副作用不在此列，例如回调最多触发一次、重试不重复写入，这些断言必须保留。

测试方法由[测试方法目录](test-methods.md)选择，运行阶段由[按阶段运行测试](test-execution.md)决定。冒烟是已有用例中的快速、确定子集，不另写一套。

## 6. 精简和删除

只有契约、故障模式和验证环境都已被另一条用例承接时，才删除重复用例，保留层级最低、区分力最强的一处；变化探测用例和已被契约用例完整承接的单次复现可以删除。长期跳过、空断言或说不清判错依据的用例先核查，不按运行历史直接删。

删除时写明承接用例。说不清承接关系就保留并记录。同一用例在多套构建或门禁里重复执行，要对应不同的故障检出能力，例如不同构建模式、运行时版本，或开启内存/数据竞争检查工具的运行；产物、配置和验证目标都没有差别时才去重。

正例：两条用例都只断言“满载返回拒绝”，保留同时检查额度归还的那条，删掉另一条，并在提交说明里写明承接关系。

反例：为了让测试数量好看，删掉唯一覆盖 Close 后迟到回调的用例；或者用 fake 的成功结果替代唯一一条验证真实断线错误传播的集成用例。

## 7. badcase 进入测试契约，而不是历史正文

新 badcase 如果揭示了当前行为要求，就把它写成能区分错误实现的回归用例，并同步修正代码、当前文档和提示词中的概念。测试名、测试说明和断言都描述新行为，不只新增一个带 issue 号的测试，把旧契约留在其他文件里。

正例：接口从“已完成”改为“已接纳但结果未知”，新增 `returns_outcome_unknown_after_deadline`，断言调用者能查询或补偿；文档和 Review 检查项都使用“未知结果”。

反例：新增 `regression_213`，只说明“修复了某次问题”，断言仍按旧的成功/失败二选一，后来维护者只能读提交历史才能知道真实契约。

## 证据和停止条件

交付关键用例及契约依据、风险、可区分的错误、实际执行结果或未验证原因；删除用例时交付承接关系。失败先区分产品、测试和环境；不放宽断言、跳过失败、整套重跑或加盲目等待来凑全绿。

当关键风险已有有效用例，或未知/未覆盖项已明确记录，且新增案例不再改变结论时就停。纯文档改动用链接、内容和脱敏检查，不硬造业务测试；未经授权不在共享或生产环境注入故障，也不为单个任务搭通用测试框架。
