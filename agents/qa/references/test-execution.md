# 按阶段运行测试

**何时读**：决定开发中或合入时跑哪些测试。项目已有门禁脚本和命令时照用，这里只给选择依据。目标是开发中测试成本尽量低，合入时再放宽到全量和重型检查。

## 1. 用模块和标签选测试

每条用例属于一个模块，并按性质带一个或多个类别标记：冒烟、单元、集成、真实环境、性能；泄露检查和疲劳测试单独标记或单独构建。实际标签名和筛选命令由项目定义（例如有的项目用 `smoke`、`unit`、`integration`、`live`、`perf`），本文按类别表述。冒烟是从已有用例里挑出的少量、快速、确定、能说明模块基本可用的子集，与其他标签并存，不另写一套。

模块边界与代码模块一致，“改了哪个模块”才能直接对应到“跑哪些测试”。测试名以模块为前缀、冒烟带统一标签，就能用测试工具的标签和名称过滤一步选出“某模块的冒烟”；具体命令写在对应语言规则或项目门禁里。

正例：HTTP 用例都在 `tests/http/`，测试名都是 `http.<行为>`；改 HTTP 解析时，一条过滤就能选出 HTTP 冒烟。

反例：一个 misc 测试文件里混着 HTTP、Redis 和 config 用例，只改 config 也得把 HTTP 用例一起跑；或者冒烟没有打项目约定的冒烟标签，只能靠记忆挑。

## 2. 开发中：编码结束后，只跑相关冒烟

编码连续完成，中途只做编译和静态检查，不为每个小改动跑测试；编码阶段结束后集中测一次，不把测试散在编码过程里。多工作包任务里，每个工作包编码完成后各测一次。

编码结束后要跑的：

- 改动模块的冒烟；
- 受影响下游模块的冒烟；
- 直接验证本次行为的最小用例集，包括这次没改过的已有回归，不以测试文件是否修改为界。

受影响下游指实际使用本次受影响接口、公共类型或行为的模块，不是所有依赖该库的模块。默认只看直接使用者；变化穿透了它的边界，才沿影响链继续往下游扩，到契约被隔离处停止。上游模块没有被改，不用为它跑测试。

确定范围的顺序：先用 `git diff` 得到改动文件，按模块边界映射到模块，再取直接使用者一跳；构建系统或代码图能给出依赖关系时直接用，没有时用 include 与符号引用搜索。改了公共头、公共类型或构建配置（`CMakeLists.txt`、编译选项）时，受影响的是所有使用它们的模块，范围相应放宽，不套用单模块口径。

这时不跑：无关模块、模块全量、集成与真实环境用例、性能用例、泄露检查和疲劳测试；重型用例只按第 4 节的例外提前运行。

冒烟要少、要快、要确定。某个模块的冒烟慢到让人不想跑，先查等待、夹具和依赖成本，或换一条更轻的已有用例当冒烟。

正例：修复 HTTP 超时的错误映射，跑 HTTP 冒烟、使用该错误映射的 RPC 冒烟，再跑现有的错误映射回归，即使这次没改它，一分钟内得到结果。

反例：错误映射回归文件这次没改，于是只跑创建和关闭冒烟；或者改一行解析就本地跑全量测试加泄露检查，等二十分钟。

正例：HTTP 错误语义变化影响 RPC 响应，跑 RPC 冒烟；只改 HTTP 内部缓冲实现、对外行为不变时，不为所有依赖 HTTP 的模块跑冒烟。

反例：改了公共数据结构的字段含义，影响到 RPC 之外更远的调用者，却机械地只看一跳；或者反过来，凡是依赖这个库的模块一律跑一遍。

## 3. 合入时：放宽到全量

有行为改动时，合入门禁完成项目规定的全量用例（包括只带冒烟标签的用例），以及适用的真实环境用例、性能回归和泄露检查，具体编排按项目门禁。纯文档等没有行为改动的变更，不因此强制业务测试。CI 已经覆盖的内容，本地不重复跑一遍来“确认”。

开发中省下的检查只是推迟，不是取消：被跳过或没有实际执行的检查不算通过证据；合入门禁失败，回到对应模块定位修复，不降低门禁、不整套重跑凑全绿。

正例：开发中只跑相关冒烟，提 PR 后由 CI 跑全量、性能回归和泄露检查；CI 指出 Redis 用例失败，就只在 Redis 模块复现并修复，再推一次。

反例：合入时也只跑冒烟就宣称通过；或者因为 CI 慢，把性能回归和泄露检查从合入门禁里挪走。

## 4. 例外：本次改动就是重型风险

只有本次改动确实改变了性能特征、内存所有权、泄露风险或并发收口语义时，才把对应的性能、泄露或交错检查提前到开发中，并且只跑相关的那几条。文件位于热路径上，不等于自动要跑基准。

正例：改缓冲区池的回收逻辑，开发中就跑该模块的泄露检查用例，不等合入时才发现泄露。

反例：改了调度热路径的算法，却说“性能留给 CI”，开发中一次基准都不跑；或者只是改了热路径上的一行日志文案，也把完整基准跑一遍。

做到改动模块和受影响下游的冒烟通过、直接验证本次行为的用例已执行、重型检查交给合入门禁或已按第 4 节跑过相关几条，就可以提交。

## 5. 成本、收益与停止

先分别记录编译、链接、运行、环境准备和维护成本，避免把过滤执行用例当成减少编译成本。复用项目已有的时间、失败和稳定性记录，条件不可比时不声称提速或降本；只测与当前瓶颈有关的指标，不为统计数量搭台账或工具链。

在引入框架、并行化或额外缓存前，先删除无效工作、重复等待和不再承担独有风险的用例，确认剩余成本对应必要覆盖。性能或成本结论必须绑定候选内容、依赖、环境、命令和测量条件，未测写未测；一次通过或单次变快不能证明长期收益。

做到当前阶段的必要检查已有可追溯证据，剩余成本和未覆盖风险已明确，新增优化不再改变决策时停止。执行阶段和证据复用见下一节。

## 6. 缓存与复用

- 构建：用 ccache，复用已配置的构建目录做增量构建，不为“干净”每次删目录重配置；并行任务各用独立构建目录，ccache 目录可共享。
- 测试：同一候选内容（提交加未提交差异）、同一依赖版本、同一命令下已通过的用例不重跑；修复后先只复测上次失败的用例（如 项目定义的失败重跑命令），再按影响范围扩大。
- 缓存只用来省时间，不是证据：结果必须能追溯到当前候选和依赖版本，任一变化即失效；怀疑缓存污染时清掉重跑并说明。

正例：改完一个模块后增量构建只重编受影响文件，修复后先复测上次失败的两条用例，通过后再跑相关冒烟。

反例：每次测试前删掉构建目录整体重编；或拿上周某个提交的通过记录，当作当前候选的测试证据。
