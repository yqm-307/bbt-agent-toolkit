# 格式化与格式检查

机械格式交给语言工具，工具判断不了的语义分组、宏例外和风格取舍才由人判断。

## 工具与配置的选择

1. 目标仓已有的 formatter、配置文件、忽略范围和 CI 配置始终优先。
2. 目标仓没有配置时，可以试用本目录 `resources/` 下的候选配置：C/C++ 用 [clang-format.yaml](../resources/clang-format.yaml)（复制为 `.clang-format`），Python 用 [ruff.toml](../resources/ruff.toml)；Go 用 `gofmt` 内建规则，不造配置。候选配置不作为既有仓库的门禁，引入新配置文件属于仓库变更，需按目标仓规则取得同意。
3. 不在表内的语言先查目标仓工具；不把一种语言的行宽或命名套到另一种语言。

## 流程

1. 锁定目标仓、版本、配置和文件范围。
2. 先只读检查（`clang-format --dry-run --Werror`、`ruff format --check`、`gofmt -l` 等）。
3. 有差异时先看 diff 再写回；没有写入授权不用原地模式。格式化只改空白、换行、缩进，不顺手改命名、逻辑、API 或错误处理。
4. 写回后再检查一次，必要时再编译或跑相关检查。

## 失败与边界

- 工具缺失、配置无效、输入无法解析、版本不匹配都算失败（BLOCKED），不能当作通过；不靠忽略全部告警隐藏问题。
- 宏、生成代码、第三方代码和项目明确保留的排版例外，在配置中排除或交人工复核。
- 不自动安装工具、不隐式联网、不把工具二进制提交进仓库。
- 格式检查通过只说明符合该工具与配置，不替代编译、测试、审查或命名与设计判断。
- 交付时写明工具与版本、配置来源、实际命令与退出码、未覆盖范围。
