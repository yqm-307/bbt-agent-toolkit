# 文档与注释规则

适用于注释、README、指南、设计说明、公共规范和脱敏文本。公共接口事实写在声明旁边；文档网站只负责展示，生成页面不能反过来成为契约。

## 1. 写当前契约和必要原因

- 业务语义使用团队语言；中文团队可优先中文，跨语言开源 API 按项目语言策略。术语、API、类型、命令、错误码和协议字段保持原样，业务 payload 不为了语言统一而翻译。断言、异常和控制台诊断语言由项目规定。
- 公开类、函数、枚举、回调、资源句柄和文件职责按需写文档注释；无调用约束的默认构造、析构不机械加注释。参数、生命周期、线程和错误约束必须明确。函数、构造函数等接口以及类型本身的注释要求不因变量注释规则改变。语言语法见 [C++ 文档](../cpp/documentation.md)。
- 变量、常量和类内成员变量：含义明显时不写复述名字或直译字段名的注释；重要且简短的说明紧贴声明上方，复杂约束才展开多行。特殊值、范围、顺序、字段间条件、所有权、并发和寿命约束必须保留，不能为短而删。具体注释符号由语言或项目规则规定。

正例：`payload` 不补“载荷”；`limit` 上方说明“0 表示不限制”；顺序与借用寿命在声明旁写清。
反例：为每个成员机械添加“请求类型”“响应类型”，或为删注释而删掉“只在持锁时修改”“按插入顺序保留”的约束。
- 不复述显然操作，不堆历史叙述；并发时序、所有权、容量和资源约束不能为了短而删除。线程安全、快照一致性、Close 语义和未知结果承诺必须匹配实现。
- 注释写“现在为什么这样做”，不要把 Issue/PR 编号、阶段代号、临时行号和会话过程写成长期契约。稳定 RFC/ADR 引用可以保留，但要确认文件真实存在。

正例：

```cpp
/**
 * 差：调用 Close 关闭对象。
 */

/**
 * 好：Close 后停止接收新请求；已接收请求按契约完成、取消或报告未知结果，调用者不需要操作内部回收链。
 */
```

反例：

```cpp
/**
 * 差：TODO 下一迁移窗口会解决这个问题（没有稳定来源）。
 */

/**
 * 差：这个 getter 返回同一时刻的完整快照（实现实际上分多个锁读取）。
 */
```

好例只是写法示意，落笔前仍需核实实际行为。文档不能用更肯定的句子替代码提供不存在的保证。

## 2. 新 badcase 直接修当前正文

当前契约、正反例、代码/测试/提示词及路由同步修正，历史归追溯记录；完整规则、正反例和最低检查见 [P7](principles.md#p7)。

## 3. 文档按层级各守一件事

```text
README.md        定位、最短路由和阅读地图
原则             共同判断依据
设计文档         契约、边界和取舍
语言专项         语言写法与文档细节
仓外/私有证据    日志、审查报告、阶段计划和会话记录
```

新路由只向下引用：根路由选原则和场景，场景入口只指向自己的专项，专项不反向要求读者回到上层。这样同一事实只有一个正文，不会把规范做成互相跳转的网。

旧平铺路径若必须保留，只放短兼容说明，不能复制正文。不要为了“每个目录都有 README”预建没有独立职责的文件。

## 3. 示例、指南和决策

- 可运行示例放 `examples/<name>/`，附目的、运行方式、依赖和期望输出；断言及验收放 `tests/`。依赖外部服务的示例不伪装成普通 CI 通过。
- 稳定架构与契约放架构文档；一个决策的收益、代价和放弃方案放对应决策记录。过程日志、运行输出、审查报告和临时计划留在仓外或私有证据中。
- 公开前核对文件、命令、API、链接、许可证表述和提交元数据。区分已实现、拟议、实测、未验证和历史事实。

正例：README 只告诉读者从根路由进入哪个场景，设计文档完整解释 Close 和失败后果，测试文档给出能区分错误实现的断言。

反例：README 复制一整套规范，coding、review 和 testcase 各再抄一遍；或者链接到仓库里不存在的 `LICENSE`、脚本或测试命令。

## 4. 公开脱敏

公开内容不能包含凭据、私有地址、绝对路径、原始日志、会话标识、内部主机名或不应暴露的产品内部标识。人工全文检查、定向模式检查和自动 secret scanner 是不同证据；未运行就不能声称自动扫描通过。

正例：文档描述“固定提交”并提供公开仓库路径，私有审查证据和本机路径留在仓外。

反例：把 `.omh` 路径、内部域名、运行时 delegation ID 或原始日志片段直接写进公共正文。

## 5. 实现文件里的注释

实现文件的注释写给维护者：大多数函数 1–2 句即可，只有复杂、核心的逻辑（状态机、锁与唤醒时序、跨线程所有权转交）才写成段；只写两类——**意图**（这一步为什么存在、要达成什么）和**操作说明**（读代码要花力气才能看出的做法）。不复述语法，不写历史。

**位置**：多阶段、持锁或有时序要求的函数，在函数体第一行放整体注释，写目的、阶段列表和约束；每个阶段前再放一个短注释块，编号对应整体注释。简单函数不需要整体注释。具体形态遵循项目约定；公共契约只写在头文件声明处。

**含义**：先讲库内语义，再讲算法细节，并使用库内的原名（如 snapshot、admission、`pending_notification`）：

- 生命期：对象由谁创建、持有到何时，借用或共享到什么时候结束。
- 所有权：现在谁持有，转交给谁，转交之后原持有者还能不能用。
- 控制权：谁有权修改这个状态，靠哪把锁、哪个相位或哪个返回码保证。

**"为了避免 X"必须带例子**：写出 X 是怎么发生的——哪条路径、哪个交错、造成什么后果。写不出这样的例子，说明理由没有想清楚，删掉这句话，不要用"避免死锁""保证安全"这类结论代替。

正例：

```cpp
void WorkerPool::adjust_capacity()
{

    /**
     * 自动伸缩的一拍：把负载折成"该扩 / 该缩"信号，连续命中足够多拍才调整目标数。
     *   1. 门禁  2. 采样  3. 累计  4. 决策  5. 唤醒
     * 控制权：目标数只在 lifecycle_mutex 下改；手动入口持同一把锁，所以手动请求先到时，
     * 本拍持锁复查发现已是 manual 就放弃。
     * 为什么要"连续命中"：避免抖动带来来回伸缩。例：队列水位一拍内冲高又回落，单拍触发会先扩出
     * 线程、下一拍又缩回去。
     */
    ...

    /**
     * 5. 唤醒：notify 的所有权从 apply_target_locked 交给本函数，必须退出全部锁后再发布。
     * 被唤醒的 worker 没有本地任务时会走 try_steal 取 map 锁，锁内唤醒只会让它一醒就撞上我们手里的锁。
     */
    publish_notify();
}
```

反例（括号里是读者的疑问）：

```cpp
/**
 * 差：这里先释放锁，避免死锁。（哪两把锁、哪两条路径？读者无法检验）
 */

/**
 * 差：这里加 1。（复述操作，没有意图）
 */

/**
 * 差：用 shared_ptr 保证安全。（谁的生命期、被谁借用，都没有说）
 */
```

写完逐条核对注释里的断言：锁序、线程归属、"不会为空"之类的话必须能在代码或锁序文档里找到依据；找不到就改成已知事实，不要用更肯定的措辞替代码承诺。

**做到什么程度算够**：读者能从文档知道当前契约、适用层级、真实入口和限制；示例不制造不存在的能力；注释没有把实现偶然性升级为公共承诺；复杂函数有体内整体注释，注释断言有依据；发布前路径、链接、空白和敏感内容均有对应检查。

## 注释的信息增量



- 含混能用准确命名或直接写法消除时，先改善代码；删逐行翻译、装饰性分隔和开发流水账，不为删注释制造 helper。
- 保留契约、单位/边界、不变量、所有权、并发时序、复杂算法摘要和非显然取舍。推导成本很高的信息也值得说明，不机械要求“只能 WHY”。
- 一处事实尽量一处说明，附近引用而非复制；代码变更同步更新注释。法律声明、许可证和有追踪价值的 Issue/TODO 链接不当噪声删除。
- 注释与代码冲突先核契约和测试，不用实现自动覆盖意图；注释掉的旧实现须确认废弃且在授权范围才移除。示例、法律文本与解释性伪代码不是死代码。

## 公共接口至少说明什么

- 一句可扫描的结果摘要，不写实现过程；需要展开时空一行再写正文。
- 参数约束和输出/输入输出方向；返回结果、每类错误及失败状态。
- 前置/后置条件、线程安全、生命周期和关闭顺序；只在项目允许且调用者需要时写异常契约。
- 重要使用约束、误用或数据损失风险；废弃接口提供替代路径。

不能从名字推断工具不知道的保证；缺事实先读调用方和契约，不为每个函数补空标签。注释补充不授权修改函数签名、行为、错误集合或资源寿命。公共类型和成员采用相同原则。Doxygen 标签、示例和解析边界见 [C++ 文档注释](../cpp/documentation.md)。

导出先在临时目录生成并核告警、缺失符号和页面，生成物放忽略的构建目录，不复制回源码树。文档生成无告警不代表 API 契约正确，也不代表代码能编译。保留图源，标清事实、设计或示意，自动代码图不证明运行时顺序。
