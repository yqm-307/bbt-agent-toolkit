# 代码品位：显式机制，克制抽象

职责做窄，语义做实，机制显式，封装克制。目标是降低总理解与修改成本，不追求最少行数、零注释或最多复用。

## 适用边界

目标仓契约、语言标准、依赖和工具配置优先。不能为审美改变公共 API、错误集合、副作用次数与顺序、条件求值、资源寿命或安全检查。不能把一个项目的调度时序、错误码、线程数、停机协议或构建开关写成通用要求，也不把 C++ 命名和资源实现套到其他语言。

没有具体问题就保持原样。减少承诺须确认消费者与授权，不靠删需求获得简单。审查只给建议，不自动修改。

<a id="流程与复用"></a>
## 改动阶梯与行为保持

在理解需求和真实调用关系后，依次考虑不新增能力、已有实现、标准库、平台原生能力、已安装依赖、直接实现。停在第一个满足明确需求和边界的方案，不为走阶梯做无界调查。

- 少量重复未必需要抽象；稳定的语义边界或独立客户端已明确时，也不必等待重复出现才设计接口。
- 减少文件、依赖和跳转是手段，不能以最少行数牺牲可读性、求值语义、错误处理或测试。
- 共享根因在共同位置修复；先核调用方真实差异，不因表面相似强行合并。
- 一个函数表达一个逻辑操作，按语义而非行数划分。早退必须保持错误集合、副作用次数与顺序、资源释放、日志、审计、计数、回调和公共失败语义。
- 提取函数必须命名独立概念、隐藏细节或统一同一规则。只转发参数、增加跳转无益；清楚的局部判断不必建立 helper。
- 保留原有求值条件与次数，不能把条件读取、调用或参数求值提前为无条件执行。
- 不设函数行数或参数数量硬阈值，不强制 getter/setter、接口、设计模式、DRY 或 TDD，不为套规则新增框架或顺手清理周边。
- 不以整洁为由将错误码改成异常、借用改成复制，或删必要的空值检查。行为保持优先于审美，等价排版与个人偏好不算缺陷。

信任边界校验、防数据丢失、安全、无障碍、明确需求和必要行为检查不能为“小 diff”删掉。非平凡逻辑保留能区分关键错误的可运行检查。

<a id="职责与抽象"></a>
## 职责与抽象

模块难以理解时，先区分问题本身与额外承诺。检查它是否兼管别人的生命周期、策略、兼容或资源。只有需求确实不需要、消费者已核对且变更获授权，才缩小承诺。删除需求、错误路径或安全检查不算简化。

复杂度由拥有必要信息与控制能力的层承担。底层提供可组合原语，上层负责业务策略。不要固定套用“业务/资源/调度”三层，边界由真实消费者和变化原因决定。

提取前问：

1. **稳定语义能命名吗？** 多处是否必须随同一知识或不变量改变，而不是只长得像？
2. **消费者少知道细节了吗？** 是否仍保有完成真实工作的必要控制，不必频繁穿透封装？
3. **总成本下降了吗？** 一起看调用点、实现、错误处理、测试与调试，不只数重复行。

任一项没有依据，先保留直接写法或修局部命名。一个真实消费者也可以需要清晰语义边界；多个调用点也可能只是偶然相似，不设“几次重复才能提取”的门槛。公共 API 变更另核兼容与授权。

<a id="对象负责自己的状态"></a>
## 状态与文件职责

内部状态多或对外操作多的对象应封装可变状态，由对象维护不变量，不能让调用者先取内部锁再逐字段拼接状态操作。纯数据记录、协议值视图和 Stats/Options 快照不因字段多就强行变成行为对象。职责判断见[所有权与并发](ownership-and-concurrency.md)。

文件表达一个职责。类头聚焦所属类；共享常量、独立接口按职责放置，类专属常量可留类内。文件名表达它提供的类或明确职责，声明与实现可对应定位，不把无关实现随手分散。真正零散、无状态的辅助才放进具名工具文件，不建通用 Utils 杂物箱。内聚的附属值类型不机械拆成一类型一文件，文件长度只提示审查，不证明多职责。

正例：`Queue.hpp` / `Queue.cc` 承载队列，独立的编码接口放 `Encoder.hpp`；字节无状态操作放 `ByteOrder.hpp`。

反例：`Queue.hpp` 同时放共享协议常量、编码器和连接状态；`Utils.hpp` 收容所有不好命名的东西；`Queue.cc` 根本没有队列职责。

## 简单接口，完整协议

接口说清“做什么”和调用者需要遵守的前提；复杂机制集中到负责它的内部，不把所有实现暴露出去。跨线程或异步工作必须能回答：

- 谁拥有对象，谁只是借用，何时转移责任？
- 何时发布有效状态，失败后保留什么？
- 谁有权完成和清理，取消、超时或重复通知怎样仲裁？

同步代码没有这些竞争，就不强加状态机、代际、注册表或取消协议。确有竞争才使用最小充分机制；引用计数、原子字段或日志本身不是完整协议。

## 内部命名与测试边界

内部名称表达当前职责，不把历史版本或迁移阶段写进名字。协议版本、公开契约、生成命名空间和路径、测试名称以及 ADR 的真实版本信息不按内部命名处理，不能据此机械重命名公共符号。

测试注入变量、专用访问器和测试动作应隔离在明确的测试支撑边界，不与正式逻辑混在同一生产文件。确需生产路径接缝时只保留窄而明确的接入，不泄漏测试控制状态。

## 复用与扩展

先复用既有代码、标准能力和已采用的成熟依赖，再写最小适配。直接调用现成后端足够时，不添加 Port/Factory/Manager 链；为稳定边界或真实替换需求设置接口，不为想象中的后端数量建框架。

通用实现与资源治理不一定集中在同一个类。可组合的小能力优于全包框架，但不为“解耦”增加只有转发的 wrapper。包装器必须承担真实的契约、适配或兼容责任，否则直接调用已有入口。

死分支、重复设定已成立的状态及同规则重复实现须结合调用链审查。相似代码仅是线索，先核语义、求值、副作用和错误顺序，再决定是否共用。

## 有限方案与优化

单实现、固定容量、串行执行等方案满足当前需求即可。说明适用范围、达到上限时的失败行为和升级信号，不把“以后优化”当说明。代码需要留说明时沿用项目注释习惯，有明确简化上限可写 `ponytail:` 注释，不对普通代码机械加标签。

优化先获得真实瓶颈或正确性缺口。锁、位打包、模板、继承都只是工具：短小不等于简单，lock-free 不自动更快，现代特性不自动更清楚。诊断容许陈旧不授权数据竞争。

少封装不等于少校验；机械重复可删，信任边界不能删。显式机制不等于业务调用者必须理解底层所有细节，要把必要控制与实现泄漏分开。简单类可以直接构造，复杂有效性可以建立工厂，不一律禁止或要求工厂。观测成本、特殊生命周期或平台限制需要证据和说明。已证实的泄漏、悬空和数据竞争不能因“跟周围风格”而保留，修复仍遵守授权与验收边界。
