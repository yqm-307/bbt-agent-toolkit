# 命名与文件职责


## 命名与接口

- 用已有领域术语，同一概念同一词；名字匹配作用域，单位、端点和副作用可辨认。对长度、时间、字节数、比率等容易混淆的数值，把单位写进名字或类型，让调用点无需跳转就能判断换算是否正确，如 `timeout_ms`、`size_bytes`、`ratio_pct`。`Data`、`Info`、`Manager` 不是禁词，但不能掩盖不清楚的职责；读取操作不能悄悄创建、消费或持久化。
- 调用点有歧义时，优先现成类型、枚举、结果结构、具名参数或常量；不为每个值包类型，不用任意字符串替代有限选项。
- 参数多或布尔标志只是检查线索，不是缺陷。明确布尔属性可保留；已发布接口不能因审美变更，也不能仅凭仓内无调用判定可删。


## 函数命名

- 编码时按这里取名，审查时按末尾问句核对。名字先说行为：多数是「动词 + 对象」，动词在前，一眼看出做什么。
- 结构为 `动词_对象[_限定]`，限定用简单介词串接：`by`（按什么条件）、`for`（为谁）、`from` / `to`（来源 / 去向）、`with`、`in`。一般 2～5 个词；超过 6 个词通常说明函数做太多，或该把条件收进参数、类型。
- 大小写按目标仓声明采用的取值：snake_case 仓写 `get_order_info_by_id`，PascalCase 仓写 `GetOrderInfoById`。同一文件不混用。
- 核心动词按下表取，语义以表为准；表外动词可以用，但须是简单、常见的动词。

| 意图 | 动词 | 约定 |
|---|---|---|
| 读取 | `get` | 取内存里已有或已加载的数据；轻量、无副作用，读取不得悄悄创建、消费或持久化（见上一节） |
| 读取 | `query` | 跨进程、查库、远程或按条件查询；可能慢、可能失败 |
| 读取 | `find` | 查找，可能找不到；调用方要处理「没有」的情况 |
| 读取 | `load` | 从存储、文件、配置读入内存 |
| 计算 | `calc` | 纯计算，不改状态 |
| 判断 | `check` | 校验条件，返回 bool 或错误码，不改状态 |
| 判断 | `is` / `has` / `can` | 返回 bool 的谓词 |
| 修改 | `set` | 直接赋值 |
| 修改 | `add` / `del` | 增、删；仓内在 `del` 与 `remove` 中选一个，不混用 |
| 修改 | `update` | 按规则刷新已有状态；主动调用的周期刷新也用它 |
| 修改 | `save` | 写回存储 |
| 修改 | `reset` / `clear` | 恢复初值 / 清空 |
| 执行 | `do` | 执行一个完整业务动作，如 `do_sign_in`；有具体动词就用具体动词，`do` 不是万能前缀 |
| 执行 | `handle` | 处理收到的请求、消息 |
| 通信 | `send` / `recv` / `notify` | 发送 / 接收 / 主动通知 |
| 生命周期 | `init` / `start` / `stop` / `create` / `destroy` / `open` / `close` | 成对使用 |
| 回调 | `on_<事件>` | 被框架或他人调用的回调；事件用名词或动词原形，如 `on_login`、`on_recv_msg` |

可扫描版本维护完整的允许词表与替换表，新增核心动词先改本节语义。

- `on_<事件>` 与 `update` 不同：`update` 是主动调用，调用方决定何时刷新；`on_<事件>` 是被驱动的回调，由框架或事件源在事件发生时调用，如引擎逐帧驱动的 `on_update`。框架回调写成 `update_login` 看不出是谁触发的，应写 `on_login`。
- 简单达意：名词和动词都用简单常见的词，不为显得专业用复杂词。代表性替换：
  - `calculate` / `compute` → `calc`
  - `validate` / `examine` → `check`
  - `initialize` → `init`
  - `retrieve` / `obtain` / `fetch` → `get` 或 `query`，按上表语义选
  - `persist` → `save`
  - `transmit` → `send`
- 领域惯用语保持原词：锁和信号量的 `acquire` / `release`，加密的 `verify` / `encrypt`。
- 单个词就能达意的惯用名可直接用，如 `size`、`count`、`close`、`empty` 这类访问器或状态词；`As`/`From`/`To` 开头的转换函数是惯用法，如 `as_string`、`from_payload`。
- 不口语、不空泛：不用 `grab`、`stuff`、`foo` 这类口语或占位词；不用 `do_work`、`process_data`、`handle_it` 这类名字，动词后要有具体对象。
- 接受中式英语：按中文业务说法直译，顺序为「动作 → 对象 → 条件」，可读即可，不追求地道。
  - 领取排行奖励 → `get_reward_by_rank_idx`
  - 根据订单 id 查询订单详情 → `get_order_info_by_id`（订单已在内存；要查库时按上表写 `query_order_info_by_id`）
  - 获取用户微信绑定信息 → `get_wx_account_info_by_userid`
- 同一概念全仓用同一个已有的业务术语：奖励统一用 `reward`，不混用 `award`、`bonus`。
- 只用约定俗成的缩写，如 `id`、`idx`、`num`、`cfg`、`msg`、`err`；项目已约定的业务缩写照用；不自造缩写。
- 豁免（与可扫描版本一致）：构造与析构、运算符重载、`main`、测试框架宏、带 `override` 的覆写（名字由基类定）、与标准库容器和迭代器兼容的接口名（如 `begin`、`size`）、已发布的对外接口。已发布接口不为命名风格改名；存量改名先核消费者与兼容。

审查时问：
1. 首词是不是行为动词，且符合上表语义？`get` 有没有副作用，`check` 有没有改状态？
2. 名字和实际行为、副作用一致吗？
3. 词是否简单、无口语、无自造缩写？
4. 同一概念和仓内已有用词一致吗？


## 文件与项目命名

文件按紧密相关的概念组织，避免大杂烩和每类一文件的机械拆分。目录、文件后缀、大小写、成员前缀、接口类和指针别名采用目标仓声明的取值，不在通用规范固定。

名字长短匹配作用域；下标 `i` 合理，公开 API 不删字母缩写；单位和布尔含义明确，如 `timeout_ms`。同一文件不混用命名风格。`const` 不意味着编译期常量，不仅凭 const 改用常量命名。

C++ 标识符必须遵守语言保留名规则：下划线紧接大写字母、包含双下划线的名字在任何作用域都保留；历史惯例不能豁免。存量改名先核消费者、兼容与授权。

正例：`timeout_ms` 明确单位，`is_enabled` 表达布尔属性。
反例：读取操作叫 `get`，实际却创建持久化记录；为跟命名风格而破坏既有公共 API。
