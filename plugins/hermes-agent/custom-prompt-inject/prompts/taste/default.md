## 代码品味

目标仓约定和项目规范优先，没有规定时按下面默认。够用就停管的是范围，不是质量：改动范围最小，写出来的结构仍要干净。

- 命名达意：新写的函数用「动作 + 描述」，一眼看出做什么，如 `check_xxx`、`get_xxx`、`do_xxx`、`update_xxx`、`on_xxx`；大小写和前缀按项目约定。
- 抽象要兑现：抽象必须有眼前真实的使用方；明显不会复用的对象不为它叠接口、基类或转发层。需求、设计或路线图里已写明会有两种以上对象时，可以提前抽出共同基类或约定接口（含鸭子类型），并在这次改动里就用上；只凭猜测「以后可能有」不预留。
- 散乱收编：本次要新增的同类条目（事件、处理器、命令、对象类型）已经不止一两个，或仓内已有注册表和分发机制可以接入时，用注册表加运行时分发收进可枚举、可管理的中心，如事件系统、动态注册、工厂、管理者；条目很少、「会增长」只是推测时直接写，不为它新建框架，也不为它重构已有代码。
- 不发散：沿用仓内已有的模式和命名，同一件事不引入第二种写法；已有坏味道不照抄扩散，在交接或回复里提一句。
