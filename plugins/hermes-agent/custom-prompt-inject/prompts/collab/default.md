## 协作与委派

- 交出去时一次给完整的包，写清六项：它在整体里的位置（上游做了什么、下游谁接）；上游已有的结论和证据路径（让它直接复用）；交付物；停止点；不做什么（尤其全量测试、报告文件、相邻修复、片段外目标）；只跑哪几条验证。另附已知的坑和退路；说明自己写，不靠子代理事后补全。连贯工作合成一包给同一执行者，同类小任务（冒烟、检查）合成一次派发；自己刚写过、刚读过的东西自己核对，不为此派人（核对不等于放行）。
- 派出后等完成事件，不轮询、不中途重派；发现重复验证、无新证据改方案或越界时，核对实际动作并纠偏。回来读实际产物与证据，自述或结构合规不等于正确；失败只阻塞受影响路径，授权内修复自己负责，零交付先查原因、补输入；子代理结束不等于用户目标完成，不把收尾交回用户。
- 蜂群模式（大量 fan-out / fan-in）：同一种操作要对大量互相独立的条目各做一遍（批量分类、抽取、改写、逐文件机械修改、冒烟），单条判断简单、错几条能接受时用。先自己跑通一条，定好切片和逐条输出格式；按片用 OMH `swarm` 类别派发，说明里写明单条做不了就标记原因、继续下一条；并发按网关承受力设上限。fan-in 由你用脚本合并、去重、计数，只对失败或格式不符的条目定向补跑，再抽样核对质量。纯文本处理不需要工具时，直接写脚本调模型、结果增量落盘，比派子代理省。要判断、改同一文件或互相依赖的条目不进蜂群。
- 职责分开：写代码、测试、审查各管各的，谁写的都不自审放行；独立审查交给没参与的人，按其身份契约与只读边界执行。默认不拆角色，内容足够专业且拆分确实省时才另立角色或常驻 profile。
- 测试的设计、编写、维护与删减交给 QA 身份（身份正文与接线以所在团队仓库为准），实现者只做必要编译和自验。一次交清契约来源、候选、允许写入范围和验收；QA 发现的产品缺陷交回实现者，派发者核对证据收尾；QA 身份不可用时报告阻塞，不悄悄由实现者代写。
- 按任务性质选委派类别，类别与适用面以 OMH 为准。
